# 智能选股助手 · 用户需求规格说明书

## 高密度摘要

**文档类型**：TR1 用户需求规格说明书

**材料概要**：
`init-aireq-template.md`（权威级，源于前期澄清与确认）+ `docs/spec/插件化选股系统-总体架构设计文档.md`（参考级，选股引擎架构与异步执行建议）+ `stock_selector_api` 源码与 README（权威级，后端模板能力边界）

**产品定位**：个人自用选股工具客户端。UniApp 一套代码适配手机与 PC，通过 `stock_selector_api` 统一后端完成：选股信号获取（只查询独立选股插件、不做计算）、结果快照落库与历史浏览、**持仓诊断（外部调度把当前持仓发给插件，插件统一判断买卖/加仓并计算收益）**、通知渠道/订阅策略配置、选股/诊断结果 push（webhook）与站内信兜底。

**全局强约束（填写时必须遵守）**：

- 选股插件（`stock_selector`）为独立 HTTP 服务，`stock_selector_api` **不内嵌、不重写任何选股计算**，仅查询插件给出的信号（code/name/signal/reason）
- 定时任务**不放入 FastAPI**，由外部独立调度服务管理：查插件 → 信号导入后端（`POST /select/import`）→ 落库 + 推送
- 结果落库采用**运行快照模型**：`select_runs`（头表）+ `select_results`（明细表），按自然日分组展示
- 通知能力完全复用现有 `notify_service`（企微/钉钉/飞书/邮箱 webhook + 订阅策略 + AES-GCM 密钥落盘），**不引入 UniPush/个推厂商通道**；客户端经 **WebSocket**（`/ws/notify`）实时接收消息并弹安卓本地通知，断线由站内信按 `since` 补齐
- 支持**多账号登录**（复用既有 `sys_users` 认证体系）：选股历史、站内信、通知渠道**按用户隔离**；订阅策略为**全局共享**一套（发送时取接收用户的渠道）；外部调度导入产生的选股运行标记为**系统级**，对所有用户可见
- **持仓诊断**采用与回测一致的**统一判定架构**：当前持仓（**手动录入 + 导入券商相关记录**，按用户隔离）由外部调度服务定时发给独立选股插件，插件**统一判断买入/卖出/加仓**并返回**收益快照**（最新价/市值/浮动盈亏）；`stock_selector_api` 不内置任何买卖判断与收益计算，仅代理、落库、展示；持仓诊断只对**已有持仓**做判断，**新买入候选**仍由选股信号产出（两者分开、各调插件）
- App 为 4 个主 Tab（选股 / 结果 / 消息 / 设置），手机端底部 Tab、PC 宽屏左侧栏，同一套代码响应式
- 支持 **App 版本管理**：启动检查最新版本（`GET /api/v1/app/version`），Android 整包 APK 下载+系统安装，**可选/强制**双更新策略；H5 形态仅提示刷新不下载（安装包由使用者在后端托管目录手动上传）
- 不做个股 K 线图、不做自选股/关注列表、不做 UniApp 内用户/角色/权限/菜单管理页
- **禁止**：使用"合理 / 适当 / 较好 / 尽量 / 性能好 / 适当考虑"等模糊词

## 1 详细用户需求规格

### 1.1 价值根特性 1：选股（查询插件信号 → 快照落库 → 历史浏览）

#### 1.1.1 用户场景分析

##### 1.1.1.1 用户现状旅程

**目标客户角色**：个人投资者 / 选股工具使用者（核心）；平台管理员（使用者本人）

**现状旅程描述**：

| 阶段 | 角色行为 | 使用工具/方式 | 痛点/感受 |
|---|---|---|---|
| 触发选股 | 收盘后想看今日命中"趋势回踩/箱体突破"的股票 | 远程 SSH 登录服务器执行 `python -m stock_selector.main` | 必须依赖终端与服务器，手机无法查看 |
| 查看结果 | 阅读命令行输出的 JSON/文本结果 | 终端日志 | 结果不落库，翻历史只能翻 shell 历史与日志文件 |
| 定时复盘 | 每天手动重复执行同一命令 | 手动计划 | 坚持困难，容易漏跑，无法获得"每日自动"体验 |
| 结果通知 | 想知道结果还得再次登录查看 | 无主动通知 | 无推送通道，结果出了不知道 |

##### 1.1.1.2 用户场景建模

**三级场景建模**：

| 一级场景（When） | 二级场景（What） | 三级场景（How） | 主流方案现状 |
|---|---|---|---|
| 收盘后（每日定时） | 自动获得当日选股信号 | 外部调度服务查独立选股插件 → 获取信号 → 导入后端 → 落库并推送通知 | 同花顺/东财等 App 提供"每日选股/策略筛选"，需订阅或付费，信号规则不透明 |
| 临时想看（随机时间） | 手动触发一次选股 | App 选股 Tab 勾选策略 → "立即选股" → 后端异步代理插件查询 → 完成后展示结果 | 主流 App 直接内置自研策略，不可带自定策略 |
| 回顾历史（随时） | 查看某天/某次运行的命中信号 | App 结果 Tab 按自然日分组 → 点开展开该次运行的 code/name/signal/reason | 主流 App 提供"历史复盘/选股记录"，付费功能居多 |

##### 1.1.1.3 用户场景痛点总结

**痛点列表（按严重程度排序）**：

1. **痛点 1**：选股必须登录服务器用命令行执行，手机/普通电脑无法随时触达。
   - 来源：个人使用反馈（自身体验）
   - 影响范围：全部选股场景
2. **痛点 2**：结果不持久化，无法按日期回看历史命中信号，复盘只能翻日志。
   - 来源：个人使用反馈
   - 影响范围：选股复盘场景
3. **痛点 3**：无主动通知，选股完成不会告知使用者，定时订阅只能依赖手动跑。
   - 来源：个人使用反馈
   - 影响范围：定时复盘场景

##### 1.1.1.4 本特性价值规划结论

**价值点 1**：把"命令行选股"升级为"手机/PC 随时查看 + 定时自动选股"

**核心效果**：
1. 选股操作从"SSH+命令行"变为"App 点击"（操作步骤 ≤3 步）
2. 历史选股结果全部落库，按自然日可回看，无需翻日志
3. 后端不承担任何选股计算，仅代理查询独立插件信号——计算与展示解耦，选股插件无侵入

##### 1.1.1.5 竞争对手分析结论

**主要竞品对比**：

| 竞品名称 | 核心能力 | 差距/机会点 | 借鉴意义 |
|---|---|---|---|
| 同花顺/东方财富 App | 内置策略筛选与选股，手机端体验成熟 | 策略算法不透明、需订阅 | 验证"手机查看选股结果 + 按日分组"交互形态 |
| 私人量化脚本 | 自定义策略自由度高 | 无界面、无通知 | 仅需补齐"界面 + 落库 + 通知"，不改变选股能力本身 |

*本产品定位为个人工具，竞品分析仅作交互形态参考，不构成功能对标。*

#### 1.1.2 设计策略总结

##### 1.1.2.1 设计意图/目标

**【设计意图】**：选股引擎保持独立，客户端与后端只消费插件信号，用最薄的接入层补齐"界面、落库、通知"三件事。

**【设计目标】**：
1. 选股执行异步化：提交即时返回任务 ID，前端轮询，长任务不阻塞 HTTP（对齐引擎架构 §6.3 异步执行建议）
2. 历史落库快照化：一次运行一次快照，按自然日分组可回看
3. 前端选股交互 ≤3 步：勾选策略 → 点击选股 → 看结果/进度

##### 1.1.2.2 设计策略

**【设计策略】**：
1. 策略原则 1：后端只做"代理查询"——策略列表与选股执行全部转发到独立插件，后端零选股逻辑
2. 策略原则 2：所有选股入口（手动/调度导入）统一收敛到快照落库与通知链路，保证手动与定时行为一致
3. 策略原则 3：长任务用异步任务模型，失败可重试且用户可感知失败原因

##### 1.1.2.3 该特性创新点总结

**【设计创新点】**：
1. 插件信号消费隔离：选股计算完全外包给独立服务，后端与前端对策略实现零耦合，插件新增策略即时可见（无版本周期）
2. 快照 + 按日聚合：同时保留"单次运行快照"与"按日期浏览"两种视角，兼顾精确复盘与日常回顾

#### 1.1.3 产品主场景 Playbook

1. **客户现状（痛点场景）**：每天想看哪些股票命中自定策略，只能 SSH 上服务器跑脚本、翻终端日志，手机上看不了、结果不留存、也不会主动通知。
2. **我们的解决方案（价值主张）**：一套手机/PC 通用的 App，点一下即触发选股；结果按日期自动入库可随时回看；定时选股由调度服务自动跑，完成后通过微信/钉钉等渠道 + 站内信通知你。
3. **核心卖点（FAB 格式）**：
   - 功能（Feature）：App 勾选策略 → 立即选股 → 按日浏览历史 + 完成通知
   - 优势（Advantage）：选股插件零侵入，信号规则透明可扩展，历史永久可查，多端通用
   - 收益（Benefit）：选股从"每日 5 分钟终端操作"→"零操作自动通知"，不复盘漏跑

#### 1.1.4 特性详细需求规格

##### 1.1.4.1 产品主特性 1：策略清单（F-1.1）

**1. 该特性的 Playbook**：让使用者知道当前有哪些可用选股策略，勾选后即可执行，策略的新增无需改前端与后端。

**2. 用户使用场景**：
- 交互稿：[待确认]（UniApp 选股 Tab：策略卡片列表 + 勾选框 + 说明）
- 进入选股 Tab → 加载策略列表（来自插件）→ 勾选一个或多个策略 → 进入"立即选股"流程。
- 异常场景：插件不可达 → 页面展示"策略服务不可达"错误与"重试"按钮，操作不丢失（保留本地勾选状态）。

**3. 该特性的需求规格约束**：

| 约束项 | 要求（可量化或可枚举） |
|---|---|
| 策略来源 | 后端代理插件 `GET /api/strategy/list`，仅支持 HTTP 直连（不引入消息队列） |
| 策略数量 | ≥2 个（trend_rebound / box_oscillate），后续插件新增自动可见 |
| 展示字段 | 策略名称 + 中文说明（由后端从插件响应整理）；插件不可达时返回可读错误 |
| 刷新方式 | 进入页面即加载一次，支持下拉/点击刷新 |

**4. 遗留问题/关键劣势**：策略参数（如回踩 5%）由插件内部配置，客户端不提供参数编辑。规避：参数调整属插件侧能力，超出本版本范围，文档说明即可。

##### 1.1.4.2 产品主特性 2：立即选股与异步任务（F-1.2）

**1. 该特性的 Playbook**：使用者勾选策略后一键执行选股，后台异步查询插件信号，执行期间可感知进度，完成即展示。

**2. 用户使用场景**：
- 交互稿：[待确认]
- 勾选策略 → 点"立即选股" → 提交（返回 run_id）→ 任务卡片显示"运行中"+ 消耗时长 → 完成后自动切换为结果明细，可跳转结果 Tab。
- 异常场景：插件查询失败 → 任务置为"失败"+ 展示错误原因；重试策略：单次运行内对插件调用失败重试 N 次（N 可配置，默认 3 次，指数退避）。

**3. 该特性的需求规格约束**：

| 约束项 | 要求（可量化或可枚举） |
|---|---|
| 提交接口 | `POST /api/v1/select/run`（手动触发）：入参 strategies 数组（空则用插件默认策略），返回 run_id |
| 异步模型 | 后端创建 select_runs 记录（status=running）→ 后台任务代理插件 `POST /api/selector/run` → 信号落库 → status=success |
| 进度查询 | `GET /api/v1/select/tasks/{run_id}` 返回状态/结果数/耗时/错误；前端默认 3s 轮询 |
| 超时兜底 | 单次运行整体超时上限默认 30 分钟（可配置），超时标记 failed |
| 并发限制 | 同一时刻仅允许 1 个运行中任务；已存在运行中任务时新提交返回 409 |

**4. 遗留问题/关键劣势**：手动触发的选股执行时长取决于插件扫描全市场耗时（分钟级）。规避：异步 + 轮询 + 进度展示，避免用户无反馈等待。

##### 1.1.4.3 产品主特性 3：信号落库与历史查询（F-1.3）

**1. 该特性的 Playbook**：每次运行的结果作为快照持久化，使用者按日期回看命中信号，理解每条信号的理由。

**2. 用户使用场景**：
- 交互稿：[待确认]
- 结果 Tab → 按自然日分组展示运行记录（日期 + trigger_type + 命中数）→ 点开某日 → 展开该次运行全部命中（code/name/signal/reason/extra 摘要）。

**3. 该特性的需求规格约束**：

| 约束项 | 要求（可量化或可枚举） |
|---|---|
| 落库模型 | `select_runs`（头表：owner_type(user\|system)/owner_id/trigger_type/strategies/status/result_count/started_at/finished_at/duration_ms/error）+ `select_results`（明细：run_id/code/name/signal/reason/extra JSON） |
| 唯一性 | select_results 上 (run_id, code, signal) 唯一索引，单次运行内去重 |
| 历史接口 | `GET /api/v1/select/history`：按日期分组（page/size 分页）、支持按 trigger_type/日期区间筛选；**manual 运行仅本人可见，scheduled 运行时全用户可见** |
| 明细接口 | `GET /api/v1/select/runs/{run_id}`：返回该次运行全部命中明细 |
| 存储实现 | 沿用 repositories 双实现（SQLite/Mongo 可切换），不引入新存储组件 |

**4. 遗留问题/关键劣势**：同一股票可能连续多日命中，跨日去重/趋势统计不在本版本。规避：按"运行快照"口径展示，单次运行内去重。

##### 1.1.4.4 产品主特性 4：调度导入（F-1.4）

**1. 该特性的 Playbook**：外部调度服务负责定时，通过统一导入接口把插件信号送入系统，实现"定时选股自动落库 + 自动推送"，且与手动触发行为一致。

**2. 用户使用场景**：
- 外部调度服务（如 cron / 任务编排系统）到点 → 调用选股插件 `POST /api/selector/run` 获取信号 → 调用后端 `POST /api/v1/select/import` 提交信号 → 后端落库（新建 select_runs，trigger_type=scheduled，**owner_type=system 系统级**）+ 触发全员通知。
- 使用者无需进入 App 即可获得每日结果与推送；系统级运行对所有用户可见。

**3. 该特性的需求规格约束**：

| 约束项 | 要求（可量化或可枚举） |
|---|---|
| 导入接口 | `POST /api/v1/select/import`：入参 trigger_type=scheduled、strategies、signals 数组（code/name/signal/reason/extra），返回 run_id |
| 鉴权 | 走后端统一认证（JWT/Session + 密码到期网关）；外部服务调用需持有有效令牌（部署时签发） |
| 幂等 | 同一 (trigger 批次标识) 重复导入不产生重复运行记录；重试安全 |
| 通知联动 | 导入成功/失败自动触发通知（见 Epic 2 F-2.3） |

**4. 遗留问题/关键劣势**：外部调度服务本身（触发时机、监控）不在此需求范围，需使用者自行部署维护。规避：提供接口契约与 curl 示例。

#### 1.2.4 特性详细需求规格

##### 1.2.4.1 产品主特性 1：通知渠道管理（F-2.1）

**1. 该特性的 Playbook**：每个用户各自在 App 内维护自己的企微/钉钉/飞书/邮箱 webhook 渠道，渠道列表相互隔离，发送目标即各用户自己的配置。

**2. 用户使用场景**：
- 设置 → 通知渠道 → 列表（类型/名称/启用状态，**仅本人渠道**）→ 新建/编辑（填 webhook_url、secret 等）→ 保存。
- 点"测试"→ 后端发送测试消息 → 提示成功/失败。
- 敏感字段（secret/密码）编辑回显仅显示"已配置"，不显示明文（沿用后端设计）。

**3. 该特性的需求规格约束**：

| 约束项 | 要求（可量化或可枚举） |
|---|---|
| 接口 | 复用 `GET/POST /api/v1/notify/channels`、`PUT/DELETE /channels/{key}`、`POST /channels/{key}/test` |
| 作用域 | 渠道按登录用户隔离：查询/修改/测试均以当前用户为容器，不暴露其他用户渠道 |
| 渠道类型 | 企业微信 / 钉钉（加签）/ 飞书 / 邮箱 SMTP，字段与后端 CHANNEL_TYPES 一致 |
| 密钥安全 | 敏感字段 AES-GCM 加密落盘（沿用模板），接口不回显明文，仅回传 `enabled`/已配置布尔 |
| 权限 | 需 `sys:notify:update`（写）/ `sys:notify:list`（读），未授权操作返回 403 |

**4. 遗留问题/关键劣势**：webhook 渠道依赖企业内网可达性/外网回调。规避：提供测试发送，失败即时反馈。

##### 1.2.4.2 产品主特性 2：订阅策略配置（F-2.2）

**1. 该特性的 Playbook**：管理员维护一套全局订阅策略（哪些事件 → 哪些渠道类型 → 多久推一次）；发送时系统对每个接收用户取其各自配置的渠道进行分发，控制通知频率与范围。

**2. 用户使用场景**：
- 设置 → 订阅策略 → 查看事件目录（select_completed/select_failed/login_failure/account_locked/task_failed 等）→ 总开关 + 每事件选择目标渠道类型 + 节流间隔 → 保存（全局生效）。

**3. 该特性的需求规格约束**：

| 约束项 | 要求（可量化或可枚举） |
|---|---|
| 接口 | 复用 `GET/PUT /api/v1/notify/policy`、`GET /api/v1/notify/events` |
| 作用域 | 订阅策略全局唯一共享；事件命中时按接收用户（manual=归属用户，scheduled=全体用户）分别取其渠道发送 |
| 事件 | 内置事件元数据含 select_completed（选股完成）、select_failed（选股失败）——后端新增 |
| 节流 | 每事件可配 interval（秒），中间间隔未到不重复发送 |
| 总开关 | notify_enabled 全局总闸，关闭时全部事件不发送（站内信仍写） |

**4. 遗留问题/关键劣势**：节流为简单时间窗，不支持复杂路由规则。规避：本期需求采用"事件+渠道+间隔"即可满足。

##### 1.2.4.3 产品主特性 3：选股结果推送（F-2.3）

**1. 该特性的 Playbook**：选股导入/手动完成后自动通知，触发链路与渠道配置解耦。

**2. 用户使用场景**：
- 手动选股运行完成 → 后端 emit `select_completed`（含命中数与摘要）→ 按订阅策略分发 webhook + 写站内信，接收对象为该运行归属用户。
- 系统级（调度导入）运行完成 → emit `select_completed` → 对全体用户分别分发（各取其渠道 + 站内信）。
- 运行失败 → emit `select_failed`（含错误摘要）→ 通知处置。

**3. 该特性的需求规格约束**：

| 约束项 | 要求（可量化或可枚举） |
|---|---|
| 事件 | 新增 `select_completed` / `select_failed` 内置事件定义（消息模板：命中数、日期、失败原因） |
| 分发 | 经 `notify_service` 按订阅策略发送，渠道未配置时静默（不报错） |
| 接收范围 | manual 运行→归属用户；scheduled（系统级）运行→全体用户 |
| 实时通道 | 事件触发后服务端经 WebSocket 实时推送至在线客户端（`/ws/notify`，鉴权复用统一认证，按 user_id 路由）；离线客户端以站内信同步补偿 |
| 双路 | 无论外部渠道是否成功，站内信必写 |
| 内容 | 推送/站内信内容包含：运行日期、命中股票数、前 N 条命中摘要（N 默认 5，可配置） |

**4. 遗留问题/关键劣势**：外部 webhook 送达率取决于机器人/服务可用性。规避：站内信兜底可回溯。

##### 1.2.4.4 产品主特性 4：站内信（F-2.4）

**1. 该特性的 Playbook**：系统通知（选股完成/失败等）按接收用户分别落账，用户各自在"消息"Tab 查看自己的站内信与已读状态。

**2. 用户使用场景**：
- 消息 Tab → 站内信列表（时间倒序，未读标记，**仅本人消息**）→ 点开详情 → 标记已读。
- 客户端在线时经 WebSocket 实时接收新消息，收到买入/卖出信号即弹安卓通知栏（本地通知），无需手动刷新。

**3. 该特性的需求规格约束**：

| 约束项 | 要求（可量化或可枚举） |
|---|---|
| 落库 | `inbox_messages`（id/**user_id**/type/run_id?/title/content/read_status/created_at），新增后端模型与接口 |
| 接口 | `GET /api/v1/messages`（按当前用户过滤 + 分页 + 未读数）、`PUT /api/v1/messages/{id}/read` |
| 事件覆盖 | 至少覆盖 select_completed、select_failed；后续事件可扩展 |
| 未读数 | 列表接口返回未读数，App Tab 徽标展示（按用户计算） |
| 实时接收 | 经 `uni.connectSocket` 连接 `/ws/notify` 接收新消息（心跳保活 + 自动重连）；`latest_id` 前进时触发安卓本地通知（`uni.createPushMessage`） |
| 可靠补偿 | 断线/离线期间消息由站内信持久化，重连后按 `since=<本地 latest_id>` 补齐，不丢不漏 |

**4. 遗留问题/关键劣势**：站内信仅存留系统事件，无用户间会话能力。规避：本期不涉及，明确边界。

1. 策略原则 1：复用后端认证接口（login/refresh/me/change-password），前端不重实现认证逻辑
2. 策略原则 2：响应式以"断点切换"实现——窄屏底部 Tab、宽屏左侧栏，组件复用
3. 策略原则 3：统一 HTTP 拦截器处理 401/428/429，页面级提示

##### 1.3.2.3 该特性创新点总结

**【设计创新点】**：无（标准基座能力，不在价值创新范畴）。

#### 1.3.3 产品主场景 Playbook

1. **客户现状**：没有统一入口，日常要看选股结果得开服务器。
2. **我们的解决方案**：手机扫码/账号登录后即进入 4 Tab 工作台，PC 浏览器同账号同一套界面。

##### 1.3.4.1 产品主特性 1：登录认证（F-3.1）

**4. 遗留问题/关键劣势**：Android 8.0+ 需用户授权"安装未知应用"；iOS 无分发渠道本期不做。规避：下载完成后静默引导授权页；iOS（TestFlight/App Store）留后续版本。

##### 1.4.1.4 本特性价值规划结论

**价值点 1**：把"选股信号 ÷ 持仓"的交叉判定交给插件统一执行，结果落库可回看。

**核心效果**：
1. 持仓统一录入（手动/导入券商记录），后端持久化且按用户隔离
2. 定时把当前持仓发给插件，插件统一判定买入/卖出/加仓并计算收益快照——**与回测判定逻辑同源（插件统一判定）**

#### 1.4.2 设计策略总结

##### 1.4.2.1 设计意图/目标

**【设计意图】**：以最小新增（持仓管理 + 诊断落库 + 通知）复用现有插件与通知链路，把"买卖/加仓判定"收敛到插件，与回测判定同源统一。

**【设计目标】**：
1. 持仓录入：手动逐条 + 导入券商记录（CSV/文件导入，字段映射回显确认）
2. 定时诊断：外部调度把持仓发插件 `POST /api/portfolio/analyze`，插件返回 action(buy/sell/add/hold)+reason+最新价/市值/浮动盈亏
3. 快照落库：每次诊断结果（含收益快照）按用户落库，历史可回看；新买入候选仍走选股信号（两者分开）
4. 通知复用：诊断完成走既有双路通知

##### 1.4.2.2 设计策略

**【设计策略】**：
1. 策略原则 1：判定全在插件——`stock_selector_api` 不内置任何买卖判断与行情读取，只负责持仓存取、请求插件、落库、展示、通知
2. 策略原则 2：触发仅外部调度定时（与选股一致），后端不内置定时器；不支持用户手动触发的诊断（本期明确边界）
3. 策略原则 3：持仓与诊断结果按用户隔离；仅诊断当前用户自己的持仓
4. 策略原则 4：收益快照数值以插件返回为准，后端不重算（最新价/市值/浮动盈亏原样存储展示）

##### 1.4.2.3 该特性创新点总结

**【设计创新点】**：
1. 判定同源：持仓买卖/加仓判定与回测逻辑共用"插件统一判定"架构，规则一致性可保证
2. 收益演进：每次诊断落收益快照，形成持仓收益时间线

#### 1.4.3 产品主场景 Playbook

1. **客户现状**：持仓零散记录，买卖/加仓靠人肉对照选股信号，收益不可回看。
2. **我们的解决方案**：持仓录入（手动/导入券商记录）→ 每日定时发插件统一判定 → 结果+收益快照落库 → 通知 + 历史回看。
3. **核心卖点**：
   - 功能：持仓管理 + 定时诊断 + 收益快照回看
   - 优势：判定与回测同源（插件统一判定）、后端零判断、按日快照可回溯
   - 收益：不用人肉比对选股与持仓，收益演进一目了然

#### 1.4.4 特性详细需求规格

##### 1.4.4.1 产品主特性 1：持仓录入与导入（F-4.1）

**1. 该特性的 Playbook**：用户在 App 持仓页维护自己的当前持仓（每用户一份，按用户隔离），支持手动录入与导入券商导出记录，作为诊断输入。

**2. 用户使用场景**：
- 持仓列表 Tab：查看/新增/编辑/删除持仓记录。
- 导入：选择券商导出的记录文件（CSV 等）→ 字段映射预览 → 确认导入（覆盖或追加按控件文案，默认追加；重复 code 提示）。
- 手动新增字段：代码/名称/数量/成本价；必填与格式本地即时校验。

**3. 该特性的需求规格约束**：

| 约束项 | 要求（可量化或可枚举） |
|---|---|
| 接口 | `GET/POST/PUT/DELETE /api/v1/holdings`、`POST /api/v1/holdings/import` |
| 字段 | code（6 位）/name/quantity（>0 整数）/cost_price（≥0，精度 4 位）/enabled（默认 true） |
| 隔离 | holdings 按 user_id 强隔离；越权返回无权限语义（REQ-015 同语义） |
| 数量 | 单用户持仓上限 200 条（超出拒绝并提示）；导入追加，重复 code 按"更新或跳过"策略（UI 确认） |
| 导入 | 支持券商记录文件（CSV，含表头），字段映射可回显确认；格式错误逐行报告不中断 |

**4. 遗留问题/关键劣势**：券商导出格式多样，无法穷举。规避：支持 CSV 标准列（code,name,quantity,cost_price）映射，其他格式后续扩展。

##### 1.4.4.2 产品主特性 2：定时持仓诊断与收益快照（F-4.2）

**1. 该特性的 Playbook**：外部调度服务每日定时把各用户的当前持仓发给选股插件，插件统一判定每只持仓的买入/卖出/加仓并返回收益快照，后端落库存储。

**2. 用户使用场景**：
- 外部调度（收盘后，与选股同调度）→ 对每个有持仓的用户：取该用户 holdings → 调插件 `POST /api/portfolio/analyze`（入参 holdings）→ 插件返回逐只 action + reason + last_price/market_value/pnl/pnl_pct → 后端按用户落库。
- 用户在 App 持仓/结果 Tab 查看最后一次诊断结论 + 收益快照，并按日期回看历史。

**3. 该特性的需求规格约束**：

| 约束项 | 要求（可量化或可枚举） |
|---|---|
| 触发 | 仅外部调度定时触发（后端提供一次性诊断入口 `POST /api/v1/portfolio/diagnose`，可指定 user_id 范围，缺省全部未禁用用户） |
| 判定代理 | 后端代理插件 `POST /api/portfolio/analyze`，入参参考：holdings=[{code,quantity,cost_price}]，出参含 action(buy/sell/add/hold)/reason/收益快照 |
| 判定范围 | 仅对**已有持仓**判定买卖/加仓；持仓内无 new 买入候选；**新买入候选由选股信号产出（REQ-001~005）**，两者分开 |
| 收益快照 | last_price/market_value(持仓市值)/pnl(浮动盈亏)/pnl_pct(浮盈率)，以插件返回为准存储，后端不重算 |
| 落库 | 每次诊断生成 run 头（portfolio_diag_runs：owner(user_id)、trigger=scheduled、status、持仓数、收益汇总）+ 明细（portfolio_diag_results：code/action/reason/收益快照），同 run 内 code 唯一 |
| 单一判定源 | 后端与客户端不实现任何买卖判定/收益计算（仅查询展示插件结果） |

**4. 遗留问题/关键劣势**：收益为静态快照（不实时盘中刷新）。规避：诊断仅定时触发，收益以调度时刻插件返回值为准。

##### 1.4.4.3 产品主特性 3：诊断结果落库与历史回看（F-4.3）

**1. 该特性的 Playbook**：每次诊断结论（动作/理由/收益快照）持久化，用户在 App 按日期回看历史诊断，形成收益演进时间线。

**2. 用户使用场景**：
- 结果 Tab（或独立"持仓诊断"页）：按自然日分组展示诊断运行 → 点开展开逐只 code/action/reason/收益快照。
- 通知：诊断完成后触发双路通知（外部渠道+站内信）+ 在线 WS 实时到达。

**3. 该特性的需求规格约束**：

| 约束项 | 要求（可量化或可枚举） |
|---|---|

#### 1.4.5 技术需求设计与评审结论

**技术可行性初步评估**：可行。持仓录入/导入/落库/历史查询为常规 CRUD；判定与收益计算全部依赖插件新增分析接口（复用现有判定内核），后端仅代理与存储，无新增计算复杂度。

- 插件新增 `POST /api/portfolio/analyze`：将现有 `RuleEvaluator`/回测 `evaluate_holdings` 判定逻辑封装为 HTTP 接口（复用 `rules.py`/`rule_eval.py`，不重构回测），返回 action/reason/收益快照。

- 风险 3：多用户持仓与诊断结果隔离 → 缓解：holdings/diag 均 user_id 强隔离，沿用 REQ-015 机制

## 3 附录

### 词汇表

| 术语 | 定义 |
|---|---|
| 选股插件（Plugin） | 独立运行的选股引擎服务（`stock_selector`），负责读取行情并给出信号 code/name/signal/reason |
| 选股运行（SelectRun） | 一次选股执行快照（select_runs），trigger_type=manual/scheduled，含状态与统计 |
| 命中信号（SelectResult） | 一条选股结果（select_results），code/name/signal/reason/extra |
| 持仓（Holding） | 用户当前持仓记录（holdings），code/name/quantity/cost_price，按用户隔离，作为诊断输入 |
| 持仓诊断（DiagRun） | 一次定时诊断运行（portfolio_diag_runs），输入当前持仓、输出逐只见解 + 收益快照 |
| 诊断结论（DiagResult） | 单只持仓的诊断结果（portfolio_diag_results），code/action(buy/sell/add/hold)/reason/收益快照 |
| 收益快照 | 诊断时刻插件返回的 last_price/market_value/pnl/pnl_pct，后端不重算 |
| 通知渠道（Channel） | 企微/钉钉/飞书/邮箱四类 webhook 渠道配置 |
| 订阅策略（Policy） | 事件+渠道+节流间隔的通知分发规则 |
| 站内信（Inbox） | 系统事件（选股完成/失败等）在 App 内的消息记录（inbox_messages） |
| 外部调度服务 | 调用选股插件与 `POST /select/import` 的独立定时服务（不进 FastAPI） |
| 立即选股 | 用户在 App 手动触发的选股（trigger_type=manual） |
