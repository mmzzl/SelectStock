# Tech-系统级-审计记录通道

1、【技术故事】 - TL & 模块负责人

支撑 Story2.1.3（REQ-017）的审计链路：渠道增删改、订阅策略修改、版本发布变更、登录/登出等写操作产生结构化审计记录（操作人/时间/对象/结果），只追加可查询；审计写入失败不中断业务（WARN）。

关联的系统需求编号：REQ-017；依赖 REQ-011（身份）、REQ-006/007/014 写操作接口。

2、【A/C验收条件】 - TL & 模块负责人

2.1 功能性验收条件

1、业务规则、边界：
- 审计范围：渠道增删改、订阅策略修改、版本发布变更、登录/登出。
- 审计字段：操作人、时间、操作对象、操作结果（含关键字段摘要）。
- 存储与查询：审计记录持久化，可查询（接口或 DB 检索）；只追加，无修改/删除接口。
- 审计写入失败不中断业务（WARN 日志）。

2、系统功能约束：
- 复用既有日志/存储基建；审计保留 ≥180 天可配置、到期滚动清理（LOG-05）。

3、实例化场景（正常场景和异常场景）：
- 正常：新增+删除 1 渠道 → 2 条审计记录（操作人/时间/对象/结果）可查询；改策略/登记版本各生成审计含前后摘要。
- 异常：审计存储故障 → 业务不中断、WARN 记录审计失败；越权查询审计 → 按既有鉴权拒绝/受限；普通写接口尝试修改已有审计 → 无修改接口记录不变。

2.2 非功能性验收条件

1）性能分析：审计写入不影响业务主链路（小同步开销或异步补偿，个人量级可忽略）。
2）可靠性：写入失败不阻塞业务（WARN），后续可补偿/滚动清理；日志保留 ≥90 天、审计 ≥180 天（LOG-05）。
3）可维护性：审计记录可溯源还原操作时序（LOG-03 语义）。
4）开放性：审计查询接口/DB 检索方式入文档（OPN-01）。
5）安全性：只追加不可篡改（SEC-05）；越权查询受限；token 不写日志（SEC-07）。
6）其他：可测试性——脚本执行渠道/策略/版本若干写操作，断言审计数量与关键字段逐条匹配（TES-03）。

3、【依赖与风险】 - TL & 模块负责人

1、需求关联性，内部功能依赖，外部跨团队协作：依赖 REQ-011 及 REQ-006/007/014 写操作；不涉及外部团队。
2、技术风险、测试风险：审计影响主流程性能（低）→同步写或异步补偿，个人量级开销可忽略。

4、【技术思路】 - TL & 模块负责人

1、技术如何实现，方案如何设计，指导开发：
   架构边界：审计作为横切关注点（channel/subscription/version/auth 写路径统一接入），复用既有日志/存储基建（LOG 章节）；只追加语义由存储设计保障。
2、技术方案：审计模型与埋点见服务级 Tech 文件；具体实现由开发负责人深化。
