### 【Story】Story2.1.3-写操作审计 🟡

> 来源：REQ-017（P1）

【用户故事】⭐

作为系统管理员（使用者本人兼），我想要渠道/策略/版本/登录等写操作留痕可查询，以便追溯变更历史、快速定位问题。

【场景说明】⭐

针对审计治理场景：渠道增删改、订阅策略修改、版本发布变更、登录/登出等写操作均产生审计记录（操作人/时间/对象/结果）；记录只追加、可查询。
**痛点背景**：既有后端日志为基础留痕，无结构化审计模型；诉求=结构化审计、可查询、不可篡改。
- 来源：REQ-017（关联 ch02 场景3/4）

---

【A/C 验收条件】

一、功能性验收条件 ⭐

1、业务规则：
- 审计范围：渠道增删改、订阅策略修改、版本发布变更、登录/登出。
- 审计字段：操作人、时间、操作对象、操作结果（含关键字段摘要）。
- 存储与查询：审计记录持久化，可查询（接口或 DB 检索）。
- 只追加语义：不可被普通写请求修改/删除。
- 审计写入失败不中断业务（WARN 日志）。

2、实例化场景描述：

   正常场景：写操作留痕
   Given（前提条件）：用户新增+删除各 1 个渠道
   When（行为）：操作完成
   Then（结果）：生成 2 条审计记录（操作人/时间/对象/结果），可查询

   正常场景：策略/版本留痕
   Given（前提条件）：修改订阅策略；登记一个版本
   When（行为）：操作完成
   Then（结果）：各生成审计记录，含操作前后关键字段摘要

   异常场景：审计存储失败
   Given（前提条件）：审计存储异常
   When（行为）：业务写操作
   Then（结果）：业务不被中断，WARN 日志记录审计失败

   异常场景：登录/登出留痕
   Given（前提条件）：登录与登出各一次
   When（行为）：会话变化
   Then（结果）：审计记录登录/登出时间与账号

   安全场景：只追加语义
   Given（前提条件）：已有审计记录
   When（行为）：普通写接口尝试修改它们
   Then（结果）：无修改接口，记录保持原样

   安全场景：越权查询
   Given（前提条件）：非管理员查询审计
   When（行为）：请求
   Then（结果）：按既有鉴权语义拒绝/受限

   边界场景：同一对象多操作 / 保留策略
   Given（前提条件）：同一渠道 1 分钟被改 5 次；或审计量长期增长
   When（行为）：操作 / 长期运行
   Then（结果）：5 条记录齐全、按时间可还原乱序；跟随日志保留策略（≥180 天可配置），到期自动滚动清理不阻塞业务

【操作步骤】⭐

1. 管理员执行写操作（渠道/策略/版本/登录）。
2. 系统自动写入审计记录。
3. 经审计查询接口/DB 检索留痕。

【期望效果】⭐

渠道/策略/版本/登录等写操作均产生审计记录（含人/时/对象/结果），可持续查询。

【需求规格约束】🔲

审计字段与存储格式详见总体设计；审计记录保留 ≥180 天、容量上限可配置（LOG-05）。

二、非功能性验收条件 ⭐

【产品需求】

- 可运维性：操作留痕可追溯（LOG-03）；日志滚动保留 ≥90 天、审计保留 ≥180 天可配置（LOG-05）。
- 可靠性：审计写入失败不阻塞业务（WARN 日志）。
- 可测试性：脚本执行渠道/策略/版本若干写操作，断言审计记录数量与关键字段逐条匹配（TES-03）。

【安全需求】⭐ 必填（QS-007）

- 审计只追加语义，不可被普通写接口篡改（SEC-05）。
- 审计查询按既有鉴权语义拒绝/受限（越权按无权限语义）。
- token 不写日志（SEC-07）。

【海外合规】🔲

不涉及（个人自用国内工具，QS-006 裁剪）。

【依赖与风险】⭐

3、跨团队协作（沟通/确认/附件）：不涉及。
