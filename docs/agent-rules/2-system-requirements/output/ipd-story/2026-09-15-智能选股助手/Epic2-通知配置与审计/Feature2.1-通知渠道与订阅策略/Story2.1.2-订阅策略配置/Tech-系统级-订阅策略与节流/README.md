# Tech-系统级-订阅策略与节流

1、【技术故事】 - TL & 模块负责人

支撑 Story2.1.2（REQ-007）的策略链路：全局通知订阅策略（事件 → 渠道类型列表 → 节流间隔）持久化与生效；发送时对每个接收用户按其渠道类型解析其本人渠道实例；渠道未配置静默跳过、站内信仍写入；节流时间窗防重复打扰。

关联的系统需求编号：REQ-007；依赖 REQ-006（渠道）、REQ-008（发送）、REQ-017（审计）。

2、【A/C验收条件】 - TL & 模块负责人

2.1 功能性验收条件

1、业务规则、边界：
- 策略结构：事件（select_completed/select_failed）→ 渠道类型列表（wecom/dingtalk/feishu/email）→ 节流间隔。
- 全局唯一：无 user_id，任一用户修改影响全体。
- 发送时机：事件发生时对每个接收用户按其渠道类型解析其本人渠道实例发送；渠道未配置静默跳过（站内信仍写入）。
- 节流：同一事件+渠道受时间窗约束，窗口内合并/跳过；逐事件独立计数。
- 非法事件保存返回 400"不支持的事件类型"。

2、系统功能约束：
- 策略修改审计留痕（REQ-017）；策略为全局配置，无私有数据。

3、实例化场景（正常场景和异常场景）：
- 正常：策略 completed→企微+邮箱、节流 60s；A 配企微+邮箱、B 只配企微 → 触发 completed → A 两条、B 一条；30s 内再触发不重复发送。
- 异常：用户无对应渠道 → 静默跳过站内信仍写入；非法事件 → 400 返回原因；未登录修改 → 401。

2.2 非功能性验收条件

1）性能分析：策略解析 + 节流判断开销不影响事件主链路（发送异步）。
2）易用性：策略编辑 ≤3 步（REQ-007 非功能）。
3）可维护性：策略默认值环境变量化（LOG-02）；修改写审计（LOG-03）。
4）开放性：策略 JSON 结构入 OpenAPI（OPN-01）。
5）安全性：策略接口鉴权（SEC-02）；修改审计防抵赖（SEC-05）；token 不写日志（SEC-07）。
6）其他：可测试性——多用户 + 固定策略矩阵构造事件，断言每个用户收到渠道集合 = 其渠道∩策略渠道类型（TES-03）。

3、【依赖与风险】 - TL & 模块负责人

1、需求关联性，内部功能依赖，外部跨团队协作：依赖 REQ-006/008/017；不涉及外部团队。
2、技术风险、测试风险：全局策略误改影响全员（低）→审计留痕 + 个人工具范围。
