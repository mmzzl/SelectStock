### 【Story】Story2.1.2-订阅策略配置 🟡

> 来源：REQ-007（P0）

【用户故事】⭐

作为系统管理员（使用者本人兼），我想要在设置 Tab 编辑全局订阅策略（事件→渠道类型→节流间隔），以便通知按需分发、避免重复打扰。

【场景说明】⭐

针对通知治理场景：策略为全局配置（无 user_id），任一用户修改影响全体；发送时对每个接收用户按其渠道类型解析其本人渠道实例；未配置渠道静默跳过（站内信仍写入）；节流时间窗防打扰。
**痛点背景**：无订阅策略与节流，重复事件造成消息打扰；诉求=全局策略 + 节流时间窗。
- 来源：REQ-007（关联 ch02 场景3）

---

【A/C 验收条件】

一、功能性验收条件 ⭐

1、业务规则：
- 策略结构：事件（select_completed/select_failed）→ 渠道类型列表（wecom/dingtalk/feishu/email）→ 节流间隔。
- 全局唯一：无 user_id，任一用户修改影响全体。
- 发送时机：事件发生时，对每个接收用户按其渠道类型解析其本人渠道实例发送。
- 渠道未配置静默跳过（不报错）——已配置才发；站内信始终写入（REQ-008）。
- 节流：同一事件+渠道的发送间隔受时间窗约束，窗口内合并/跳过；节流逐事件独立计数。
- 非法事件返回 400"不支持的事件类型"。

2、实例化场景描述：

   正常场景：全局策略生效 + 节流窗口
   Given（前提条件）：策略 select_completed→企微+邮箱，节流 60s；用户 A 配企微+邮箱，用户 B 只配企微
   When（行为）：触发 select_completed（system 运行）；30s 后同一事件再触发
   Then（结果）：A 收到企微+邮箱两条、B 收到企微一条；30s 窗口内不重复发送（或合并），不产生重复打扰

   异常场景：渠道未配置
   Given（前提条件）：策略配置了某渠道类型，但用户无对应渠道
   When（行为）：事件触发
   Then（结果）：该用户静默跳过，不报错，站内信仍写入

   异常场景：非法事件
   Given（前提条件）：提交不存在的 event 类型
   When（行为）：保存策略
   Then（结果）：返回 400 与原因

   安全场景：未登录修改
   Given（前提条件）：无有效 token
   When（行为）：修改策略
   Then（结果）：401

   安全场景：修改审计
   Given（前提条件）：策略被修改
   When（行为）：写审计
   Then（结果）：记录操作人/时间/对象/结果（REQ-017）

   边界场景：渠道类型为空 / 多事件多渠道
   Given（前提条件）：策略渠道类型列表为空；或 2 个事件 × 4 渠道类型矩阵
   When（行为）：事件触发 / 逐一触发
   Then（结果）：不发送任何渠道但站内信保留；按矩阵正确分发、节流逐事件独立计数

【操作步骤】⭐

1. 打开设置 Tab → 订阅策略（展示当前全局策略）。
2. 编辑某事件的渠道类型与节流间隔。
3. 保存（全局生效）。

【期望效果】⭐

策略修改全局生效；发送时按接收用户渠道解析；未配置渠道静默；编辑 ≤3 步（REQ-007 非功能）。

【需求规格约束】🔲

订阅策略保存页交互稿（设置 Tab）。

二、非功能性验收条件 ⭐

【产品需求】

- 易用性：策略编辑 ≤3 步（REQ-007 非功能）。
- 可测试性：多用户 + 固定策略矩阵构造事件，断言每个用户收到渠道集合 = 其渠道∩策略渠道类型（TES-03）。

【安全需求】⭐ 必填（QS-007）

- 策略接口鉴权（登录用户可改，管理员权限语义由后端既有鉴权承载）（SEC-02）。
- 策略修改写审计（SEC-05 / REQ-017）。
- 策略为全局配置，无私有数据泄露风险。

【海外合规】🔲

不涉及（个人自用国内工具，QS-006 裁剪）。

【依赖与风险】⭐

3、跨团队协作（沟通/确认/附件）：不涉及（复用 notify_service 策略/节流）。
