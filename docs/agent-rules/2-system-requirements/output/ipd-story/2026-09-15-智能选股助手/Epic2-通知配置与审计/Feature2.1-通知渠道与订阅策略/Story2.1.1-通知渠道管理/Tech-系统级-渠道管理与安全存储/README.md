# Tech-系统级-渠道管理与安全存储

1、【技术故事】 - TL & 模块负责人

支撑 Story2.1.1（REQ-006）的渠道管理链路：设置 Tab 维护企微/钉钉/飞书/邮箱 webhook 渠道（CRUD + 二次确认删除 + 测试发送）；密钥 AES-GCM 加密落盘、不明文返回；数据按用户强隔离。

关联的系统需求编号：REQ-006；依赖 REQ-011（认证）、REQ-017（审计）、notify 发送器（REQ-008）。

2、【A/C验收条件】 - TL & 模块负责人

2.1 功能性验收条件

1、业务规则、边界：
- 渠道 CRUD 四类 webhook；字段：名称（1~50 字符）、类型（枚举默认 wecom）、webhook 地址（合法 http(s) URL，错误实时提示）、密钥/令牌（≤200、脱敏、不回显明文）、启用/停用。
- 测试发送：向该渠道投递测试消息返回送达结果；失败返回可读原因不阻塞保存。
- 删除需二次确认；所有操作 user_id 隔离，仅作用于当前用户。

2、系统功能约束：
- 复用 notify_service 发送器做测试发送；密钥加密存储复用既有安全基建。

3、实例化场景（正常场景和异常场景）：
- 正常：新增企微渠道 → 保存 → 测试发送 → 目标机器人收到、界面反馈"送达成功"、密钥加密落盘。
- 异常：webhook 无效 → 反馈失败及原因、不影响渠道保存；B 操作 A 的渠道 → 无权限语义；导出/查看密钥 → 只返回脱敏不返回明文。

2.2 非功能性验收条件

1）性能分析：渠道 CRUD/查询 p95 ≤1s（PERF-02）。
2）易用性：新建并测试发送 ≤3 步（REQ-006 非功能）。
3）可靠性：测试发送失败不阻塞其余操作，给出可读提示（REL-06）。
4）可维护性：渠道创建/删除写审计（REQ-017）；配置环境变量化（LOG-02）。
5）安全性：AES-GCM 加密存储、不明文返回（SEC-03）；破坏性操作二次确认（REL-05）；写操作审计（SEC-05）；token 不写日志（SEC-07）。
6）其他：可测试性——webhook 指向本地 mock 端点，断言 mock 收到正确 payload、结果反馈一致（TES-03）。

3、【依赖与风险】 - TL & 模块负责人

1、需求关联性，内部功能依赖，外部跨团队协作：依赖 REQ-011/017/008；webhook 三方可达性（尽力送达）。
2、技术风险、测试风险：外部 webhook 送达率不可控（低）→测试发送 + 站内信兜底（REQ-008）。

4、【技术思路】 - TL & 模块负责人

1、技术如何实现，方案如何设计，指导开发：
   架构边界：notify 模块新增渠道持久化模型/CRUD 接口/测试发送，复用发送器与加密基建（ch06 §6.2）；渠道数据按 user_id 强制隔离（REQ-015 统一用户作用域）。
2、技术方案：渠道 CRUD 接口、测试发送服务见服务级 Tech 文件；具体实现由开发负责人深化。
