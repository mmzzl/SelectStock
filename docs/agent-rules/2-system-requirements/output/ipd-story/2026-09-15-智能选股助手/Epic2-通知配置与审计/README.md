# 【Epic】Epic2-通知配置与审计

【关键价值点】⭐

本 Epic 解决通知链路"配置不可视、错误静默丢失、变更难追踪"的治理问题。为使用者提供可达验证的通知渠道管理（企微/钉钉/飞书/邮箱 webhook）、全局订阅策略与节流防打扰，以及对渠道/策略/版本/登录等写操作的结构化审计留痕，使通知行为可配置、可验证、可追溯。

【价值实现程度】⭐

- 渠道可视化：四类 webhook 渠道按用户 CRUD，新建并测试 ≤3 步（REQ-006）。
- 策略全局生效：事件→渠道类型→节流间隔全局配置，任一用户修改影响全体（REQ-007）。
- 通知防丢：webhook 发送失败由站内信兜底，配置错误不再静默丢失（REQ-008 双路）。
- 写操作留痕：渠道/策略/版本/登录写操作 100% 记录操作人/时间/对象/结果，可查询（REQ-017）。

【用户需求设计结论】⭐

1、本 Epic 价值规划结论
   以"渠道管理 + 订阅策略 + 审计留痕"三条线构成通知治理能力：渠道提供可投递的收件箱，策略决定事件如何分发与节流，审计保证所有变更可追溯；三者均复用既有 notify_service 的渠道/策略/加密/节流能力，仅在其上补齐 API 与隔离（ch06 §6.2）。

2、目标用户与现状旅程
   目标客户角色：个人投资者（使用者本人兼系统管理员）

   | 阶段 | 角色行为 | 使用工具/方式 | 痛点/感受 |
   |---|---|---|---|
   | 配置渠道 | 在代码/配置里填 webhook 地址 | 配置文件 | 无法验证配置是否正确，不可视 |
   | 验证通知 | 改配置后手动发消息测试 | 手工 | 无测试发送能力，只能"猜" |
   | 变更追踪 | 回查渠道/策略改动 | 无手段 | 变更无记录，问题难定位 |

3、用户核心痛点（按严重程度排序）
   1. **痛点 1**：通知渠道配置不可视、不可测试，错误配置导致通知静默丢失 —— 来源：使用者自述（TR1）
   2. **痛点 2**：无订阅策略与节流，重复事件造成消息打扰 —— 来源：使用者自述（TR1）
   3. **痛点 3**：渠道/策略/版本等写操作无留痕，变更难以追溯 —— 来源：使用者自述（TR1）

4、设计策略
   - **设计意图**：复用 notify_service 既有模型/加密/节流能力，避免重造轮子（ch06 §6.2）；渠道按用户隔离、策略全局共享的归属语义与 REQ-015 隔离基线一致。
   - **设计目标**（可量化）：
     1. 渠道新建并测试 ≤3 步（REQ-006 非功能）
     2. 策略编辑 ≤3 步、修改全局生效（REQ-007 非功能）
     3. 写操作 100% 留痕，审计记录可查询（REQ-017 验收）
     4. 渠道/策略查询 p95 ≤1s（PERF-02）
   - **设计创新点**：通知信封与内容解耦 —— 通知内容固定来自 select_* 事件，投递通道完全由策略与渠道配置决定，用户可在不重发代码的情况下调整通知行为。

5、产品主场景 Playbook
   - 客户现状（痛点场景）：webhook 配置在代码里，不可测试、不可视；渠道变更无记录。
   - 解决方案（价值主张）：设置 Tab 维护渠道与策略，测试发送验证可达；发送失败站内信兜底；所有写操作审计留痕。
   - 核心卖点（FAB）：功能=渠道/策略可视化配置 + 测试发送 + 写操作审计 → 优势=通知链路可验证、配置错误有兜底、变更可追溯 → 收益=消息不静默丢失，问题可定位。

6、竞品对比结论 🔲

   不涉及（个人自用工具，无商业竞品对标；同类能力为各办公软件自带 webhook，本 Epic 的价值是统一管理与审计）。

7、关键注意事项
   - 渠道密钥必须 AES-GCM 加密落盘、不明文返回（SEC-03）；删除渠道需二次确认（REL-05）。
   - 策略为全局配置（无 user_id），修改影响全员；但发送时按"接收用户"的本人渠道实例解析（REQ-007）。
   - 审计为只追加语义，不可被普通写接口篡改；审计写入失败不阻塞业务（REQ-017）。
