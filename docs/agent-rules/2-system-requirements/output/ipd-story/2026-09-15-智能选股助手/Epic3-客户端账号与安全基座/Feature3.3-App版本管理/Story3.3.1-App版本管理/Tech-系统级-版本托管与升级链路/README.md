# Tech-系统级-版本托管与升级链路

1、【技术故事】 - TL & 模块负责人

支撑 Story3.3.1（REQ-014）的升级链路：`GET /api/v1/app/version` 检查最新发布版本 → version_code 数值比较 → force=false 可跳过 / force=true 不可跳过 → Android 整包下载（进度条）+ MD5 校验 + 授权安装 → H5 仅提示刷新。

关联的系统需求编号：REQ-014；后端版本记录 + 托管目录 + 版本接口。

2、【A/C验收条件】 - TL & 模块负责人

2.1 功能性验收条件

1、业务规则、边界：
- `GET /api/v1/app/version`：返回最新发布版本（version_code/version_name/platform/force/url/md5/size_bytes/release_notes/released_at/status）。
- 比较：以 version_code（数值）判断新旧，不以 version_name 文本。
- 更新策略：force=false 可"以后再说"跳过；force=true 不可跳过，升级完成前不可进入主界面。
- Android：uni.downloadFile（进度条）→ 校验 MD5 = url 声明的 md5 → 引导"安装未知应用"授权 → 调系统安装。
- H5（PC）：检测到新版本仅顶部提示"有新版本，请刷新"。
- 发布管理：status=enabled/disabled，disabled 不进入提示；仅返回 enabled 的最新版。

2、系统功能约束：
- APK URL 由后端托管目录生成，防任意路径；版本检查为公开路由（登录前可用）。

3、实例化场景（正常场景和异常场景）：
- 正常：新版 force=false → 启动弹"发现新版本"，点"立即升级"下载 → MD5 校验通过 → 引导授权 → 系统安装 → 新版启动；点"以后再说"关闭下次再提示。
- 异常：MD5 不一致 → 拒绝安装并删除残留、提示"安装包校验失败，请重新下载"；下载中断 → 提示失败可重试；强制更新 → 弹窗不可关闭升级前不可进主界面；本地已最新/版本接口不可达 → 无弹窗、静默放行。

2.2 非功能性验收条件

1）性能分析：版本检查接口 p95 ≤1s（PERF-02 子集）；下载展示进度。
2）兼容性：Android"安装未知应用"授权引导（COM-04）；H5 浏览器矩阵（COM-02）。
3）可维护性：版本记录管理为已有行为，本需求仅客户端接入 + 接口返回语义对齐。
4）开放性：版本接口入 OpenAPI（OPN-01）；托管目录命名规范以现有为准。
5）安全性：下载后 MD5 校验，不一致拒绝安装并删除残留（SEC-04）；APK URL 由后端托管目录生成（防任意路径）；version_code 比较防降级攻击。
6）其他：可测试性——测试 APK + 版本记录可配置（force 0/1、status enabled/disabled），模拟器验证下载/校验/安装（TES-05）。

3、【依赖与风险】 - TL & 模块负责人

1、需求关联性，内部功能依赖，外部跨团队协作：后端版本记录 + 托管目录 + 版本接口；Android 系统安装流程（产物为 APK）。
2、技术风险、测试风险：Android 授权/安装差异（中）→引导授权 + MD5 校验（TR1 §1.3.5 已评估）。

4、【技术思路】 - TL & 模块负责人

1、技术如何实现，方案如何设计，指导开发：
   架构边界：客户端版本升级模块 + 后端版本检查接口（新增） + 托管目录；强制更新决定主界面准入（ch06 §6.2 公开路由白名单）。
2、技术方案：版本接口与托管、客户端下载校验安装见服务级 Tech 文件；具体实现由开发负责人深化。
