### 【Story】Story3.2.3-多用户数据隔离与越权防护 🔴

> 来源：REQ-015（P0）

【用户故事】⭐

作为多账号用户，我想要自己的通知渠道/站内信/选股历史不被他人看到，以便测试账号与正式账号互不干扰、数据安全可靠。

【场景说明】⭐

针对数据隔离红线（SEC-01）场景：私有数据（渠道/站内信/manual 运行及明细）仅属主可见可操作；共享数据（system 运行、订阅策略）全员可见；服务端强制归属校验，越权返回无权限语义。
**痛点背景**：多账号数据不隔离将导致私有数据泄露；诉求=服务端强制隔离 + 越权无权限语义。
- 来源：REQ-015（关联 ch02 场景5）

---

【A/C 验收条件】

一、功能性验收条件 ⭐

1、业务规则：
- 私有数据范围：通知渠道、站内信、manual 选股运行及明细 → 仅属主可见/可操作。
- 共享数据范围：system 运行、订阅策略（全局）→ 全员可见/按语义操作。
- 接口级强制：查询/删除/已读/提交等操作在服务端按当前身份过滤，客户端不可绕过。
- 越权响应：无权限访问返回 404 等价或 403 级语义，不泄露资源是否存在细节。

2、实例化场景描述：

   正常场景：manual 隔离 + system 共享
   Given（前提条件）：A 有 manual 运行 r1；system 运行 r2 存在
   When（行为）：B 查询历史/明细；A、B 分别查询历史
   Then（结果）：B 看不到 r1；A/B 均可见 r2（system 全员可见）

   异常场景：越权渠道操作
   Given（前提条件）：B 修改/删除 A 的渠道 id
   When（行为）：请求
   Then（结果）：拒绝，返回无权限语义

   异常场景：越权消息已读
   Given（前提条件）：B 标记 A 的消息
   When（行为）：请求
   Then（结果）：拒绝，A 消息不受影响

   安全场景：未知 id 探测
   Given（前提条件）：B 遍历猜测 id
   When（行为）：查询
   Then（结果）：非本人资源一律拒绝，不泄露存在性细节

   安全场景：策略全局语义
   Given（前提条件）：任一用户访问订阅策略
   When（行为）：读取/修改
   Then（结果）：可读；修改按全局权限语义处理（登录用户，审计留痕 REQ-017）

   边界场景：零私有数据 / 同 run 双 owner 冲突
   Given（前提条件）：B 无任何私有数据；manual job owner 固定
   When（行为）：查询 / 提交或导入
   Then（结果）：空列表无报错；owner_type/owner_id 由服务端按触发源生成，客户端不可覆盖

【操作步骤】⭐

无需用户主动操作（系统强制规则）；越权访问的用户会收到"无权限"提示并无法获取数据。

【期望效果】⭐

跨账号访问私有数据 100% 被拒绝且不泄露；system 数据全员可见；越权返回无权限语义（REQ-015 验收）。

【需求规格约束】🔲

按用户接口清单（渠道/站内信/历史/明细等）全部接入归属过滤；见 ch03 REQ-015 与总体设计。

二、非功能性验收条件 ⭐

【产品需求】

- 安全性：归属校验为强制服务端规则，非前端控制（ch06 §6.2 架构约束）。
- 可测试性：A/B 两账号 + 全部按用户接口，脚本遍历 B 用 A 的资源 id 请求，断言 100% 拒绝（TES 工具表）。

【安全需求】⭐ 必填（QS-007）

- 多账号数据隔离（SEC-01）：私有数据仅属主可见，越权返回无权限语义。
- owner 由服务端生成、客户端不可覆盖（防越权伪装）。
- 越权 403/404 语义不泄露资源存在性；与审计联动（SEC-05）。

【海外合规】🔲

不涉及（个人自用国内工具，QS-006 裁剪）。

【依赖与风险】⭐

1、需求关联性，内部功能依赖：依赖 REQ-011（身份）、REQ-003/006/009/014（数据模型含 owner/user_id）。

3、跨团队协作（沟通/确认/附件）：不涉及（前端不承重隔离，越权防护为服务端强制规则）。
