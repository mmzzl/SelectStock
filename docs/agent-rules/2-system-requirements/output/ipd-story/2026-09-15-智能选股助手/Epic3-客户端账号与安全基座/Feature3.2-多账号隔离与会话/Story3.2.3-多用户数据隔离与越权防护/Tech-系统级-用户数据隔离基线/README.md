# Tech-系统级-用户数据隔离基线

1、【技术故事】 - TL & 模块负责人

支撑 Story3.2.3（REQ-015）的数据隔离基线：私有数据（渠道/站内信/manual 运行及明细）仅属主可见可操作；共享数据（system 运行、订阅策略）全员可见/按全局语义；服务端强制归属过滤，越权返回无权限语义。贯穿所有按用户接口。

关联的系统需求编号：REQ-015；依赖 REQ-011（身份）、REQ-003/006/009/014（数据模型含 owner/user_id）。

2、【A/C验收条件】 - TL & 模块负责人

2.1 功能性验收条件

1、业务规则、边界：
- 私有数据范围：通知渠道、站内信、manual 选股运行及明细 → 仅属主可见/可操作。
- 共享数据范围：system 运行、订阅策略（全局）→ 全员可见/按语义操作。
- 接口级强制：查询/删除/已读/提交等操作在服务端按当前身份过滤，客户端不可绕过。
- 越权响应：无权限访问返回 404 等价或 403 级语义，不泄露资源是否存在细节。

2、系统功能约束：
- 归属校验为强制服务端规则，非前端控制（ch06 §6.2 架构约束）。
- owner 由服务端按触发源生成，客户端开放字段一律不信任。

3、实例化场景（正常场景和异常场景）：
- 正常：A 的 manual 运行 r1 + system 运行 r2 → B 看不到 r1，A/B 均可见 r2；B 修改/删除 A 的渠道、标记 A 的消息 → 拒绝返回无权限语义。
- 异常：B 遍历猜测 id → 非本人资源一律拒绝不泄露存在性；任一用户读取订阅策略 → 可读，修改按全局权限语义 + 审计。

2.2 非功能性验收条件

1）性能分析：归属过滤为查询复合条件，命中索引，量级内 p95 ≤1s（PERF-02）。
2）可靠性：统一 user 作用域过滤封装，杜绝遗漏过滤点。
3）可维护性：过滤逻辑集中 service 层，按用户接口清单化盘点（REG 章节）。
4）安全性：SEC-01 红线——跨账号私有数据访问 100% 拒绝且不泄露；越权 403/404 语义防探测；与审计联动（SEC-05）。
5）其他：可测试性——A/B 两账号遍历 B 用 A 的资源 id 请求全部按用户接口，断言 100% 拒绝（TES 工具表）。

3、【依赖与风险】 - TL & 模块负责人

1、需求关联性，内部功能依赖，外部跨团队协作：依赖 REQ-011 与各数据模型接口；前端不承重隔离。
2、技术风险、测试风险：遗漏过滤点（中）→服务端统一 user 作用域过滤（按用户接口清单全覆盖）。

4、【技术思路】 - TL & 模块负责人

1、技术如何实现，方案如何设计，指导开发：
   架构边界：横切过滤——在 service 层统一追加 user 作用域条件，覆盖渠道/站内信/历史/明细等按用户接口（ch06 §6.2）。
2、技术方案：按用户作用域过滤实现见服务级 Tech 文件；具体实现由开发负责人深化。
