# Tech-系统级-账号与改密链路

1、【技术故事】 - TL & 模块负责人

支撑 Story3.2.2（REQ-013）的账号自助链路：设置 Tab 展示账号信息（`GET/PUT /api/v1/auth/me`）、修改密码（`POST /api/v1/auth/change-password`，沿用后端复杂度/历史防重用校验、错误文案原样透传）、退出登录（登出接口 + 本地清 token）。

关联的系统需求编号：REQ-013；依赖 REQ-011（认证）。

2、【A/C验收条件】 - TL & 模块负责人

2.1 功能性验收条件

1、业务规则、边界：
- 账号信息：`GET/PUT /api/v1/auth/me` 展示用户名/显示名/邮箱（可编辑展示字段视后端支持）。
- 修改密码：`POST /api/v1/auth/change-password`（旧密码 + 新密码），沿用后端复杂度/历史防重用校验，错误信息原样展示。
- 到期提示：遵循 password_expired/password_expire_warning 响应字段。
- 退出登录：调用登出接口 + 本地清 token。
- 改密表单：旧/新/确认三字段掩码必填；两次不一致本地即时提示；提交期间禁用按钮。

2、系统功能约束：
- 密码策略以服务端为准，客户端原样透传错误文案不二次猜测。

3、实例化场景（正常场景和异常场景）：
- 正常：已登录 → 展示 me 信息与接口一致；旧密码正确 + 新密码满足策略 → 改密成功提示、新密码可用。
- 异常：新密码过短/重复历史 → 拒绝、展示后端原样错误；旧密码错误 → 拒绝不改动密码；已登录登出 → token 清除业务页不可再访问。

2.2 非功能性验收条件

1）性能分析：me/改密交互 p95 ≤2s 完成往返。
2）安全性：改密后会话处理与后端约定一致；新密码不明文落日志（SEC-07）。
3）可维护性：错误文案透传机制统一封装（避免各端拼接不一致）。
4）开放性：复用既有 me/change-password 接口，不新增服务端逻辑。
5）其他：可测试性——构造失败场景断言页面文案 = 后端文案（无二次猜测）。

3、【依赖与风险】 - TL & 模块负责人

1、需求关联性，内部功能依赖，外部跨团队协作：依赖 REQ-011；不涉及外部团队。
2、技术风险、测试风险：密码策略提示一致性（低）→原样透传后端文案。

4、【技术思路】 - TL & 模块负责人

1、技术如何实现，方案如何设计，指导开发：
   架构边界：客户端账号模块（me 页/改密表单/登出），后端复用既有 auth API，不加新接口（ch06 §6.2）。
2、技术方案：me 与改密接口对接见服务级 Tech 文件；具体实现由开发负责人深化。
