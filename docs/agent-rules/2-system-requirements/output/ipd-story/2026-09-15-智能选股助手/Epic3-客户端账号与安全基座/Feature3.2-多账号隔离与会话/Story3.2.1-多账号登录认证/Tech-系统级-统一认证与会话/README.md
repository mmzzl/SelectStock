# Tech-系统级-统一认证与会话

1、【技术故事】 - TL & 模块负责人

支撑 Story3.2.1（REQ-011）的客户端认证会话链路：复用后端认证（JWT/验证码/锁定/到期网关）；access token 本地存储、401 统一拦截 + refresh 自动续期（刷新失败回登录）；密码到期 428 强制改密、到期前提示剩余天数；登出清 token。

关联的系统需求编号：REQ-011；为全部业务接口提供会话基座。

2、【A/C验收条件】 - TL & 模块负责人

2.1 功能性验收条件

1、业务规则、边界：
- 复用后端 `POST /api/v1/auth/login`（captcha_id/captcha_code）、`GET /captcha`（图片验证码）。
- 密码到期网关：428 强制改密；password_expire_warning 到期前（≤7 天）提示剩余天数。
- 锁定策略：登录失败触发锁定，429 提示锁定时长。
- token 管理：access token 存本地（非明文敏感日志）；refresh 自动续期；401 统一拦截，刷新失败回登录。
- 登出：复用登出接口 + 本地清 token。
- UI 约束：账号 4~50 字符；密码掩码；验证码图片展示；提交期间按钮禁用；登录失败不清空账号、仅清空错误字段（密码/验证码）。

2、系统功能约束：
- 会话/锁定/到期语义一律以后端为准，客户端不自行裁决。

3、实例化场景（正常场景和异常场景）：
- 正常：正确账号/密码/验证码 → 进入选股 Tab、凭证正确存储；业务 401 → 自动 refresh 重放 ≤1 次无感。
- 异常：密码/验证码错误 → 展示后端错误，不清空账号仅清空错误字段；连续失败达阈值 → 429"账号已锁定，请 X 分钟后重试"；密码到期 → 428 强制改密；登出 → 清 token 回登录页。

2.2 非功能性验收条件

1）性能分析：登录交互 ≤2s（p95）完成认证往返。
2）安全性：验证码/锁定/到期网关行为与后端一致；token 不写日志、不明文存储（SEC-07）。
3）可维护性：CAPTCHA_ENABLED 可切换（TES 工具表）；token 刷新逻辑集中封装便于复用。
4）开放性：认证接口复用既有后端，不新增服务端认证逻辑。
5）安全性补充：401 拦截 + refresh 单次重放；登录失败不泄露额外账号信息。
6）其他：可测试性——CAPTCHA_ENABLED=on/off 两态断言登录行为与后端一致。

3、【依赖与风险】 - TL & 模块负责人

1、需求关联性，内部功能依赖，外部跨团队协作：依赖后端既有 auth 模块（sys_users/JWT/验证码/锁定/到期）；客户端本能力不引入后端新改动。
2、技术风险、测试风险：验证码多端渲染差异（低）→复用后端 Base64 图片方案。

4、【技术思路】 - TL & 模块负责人

1、技术如何实现，方案如何设计，指导开发：
   架构边界：客户端 auth 模块（登录页/请求拦截/token 存储/refresh/登出），后端复用既有认证，不加新接口（ch06 §6.2）。
2、技术方案：登录认证对接、token 刷新与请求拦截见服务级 Tech 文件；具体实现由开发负责人深化。
