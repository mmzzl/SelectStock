# Tech-系统级-历史查询链路

1、【技术故事】 - TL & 模块负责人

支撑 Story1.3.2（REQ-004）的查询链路：结果 Tab 按自然日倒序分组展示运行列表（result_count/status/trigger_type/duration），点开展开命中明细（code/name/signal/reason）；分页每页 ≤50；读取按用户作用域（manual 属主可见、system 全员可见）。

关联的系统需求编号：REQ-004；依赖 REQ-003（数据源）、REQ-015（隔离）。

2、【A/C验收条件】 - TL & 模块负责人

2.1 功能性验收条件

1、业务规则、边界：
- `GET /api/select/history` 按自然日倒序分组返回运行列表；`GET /api/select/run/{run_id}` 返回明细。
- 分页：运行列表分页（每页 ≤50）；明细按需取。
- 可见性：manual 仅属主，system 全员（REQ-015）。

2、系统功能约束：
- 查询强制按当前用户过滤（服务端）；参数篡改返回无权限语义。

3、实例化场景（正常场景和异常场景）：
- 正常：多次运行 → 按自然日倒序分组，运行含 status/result_count/trigger_type；展开显示全部命中明细。
- 异常：B 访问 A 的 manual run 明细 → 无权限语义；新账号无运行 → 空态"暂无选股记录"；恶意改 run_id 探测 → 拒绝不泄露存在性。

2.2 非功能性验收条件

1）性能分析：历史查询 p95 ≤1s（PERF-02）。
2）可靠性：按日期索引保证查询稳定；个人量级可控。
3）可维护性：分组/分页参数复用统一查询 service（减少重复逻辑）。
4）开放接口：history/run 明细接口入 OpenAPI（OPN-01）。
5）安全性：强制 user 作用域过滤（SEC-01）；越权返回无权限语义不泄露资源存在性。
6）其他：可测试性——构造 N 天 M 次运行与明细，断言分组数/运行数/明细数正确（TES-03）。

3、【依赖与风险】 - TL & 模块负责人

1、需求关联性，内部功能依赖，外部跨团队协作：依赖 REQ-003/015；不涉及外部团队。
2、技术风险、测试风险：数据量大后查询慢（低）→按日期索引；个人量级可控。

4、【技术思路】 - TL & 模块负责人

1、技术如何实现，方案如何设计，指导开发：
   架构边界：select 模块新增历史查询 API（list 分页 + detail）+ 客户端结果 Tab；日期分组以 started_at 自然日截断（ch06 §6.2）。
2、技术方案：历史分组查询接口、运行明细查询接口见服务级 Tech 文件；具体实现由开发负责人深化。
