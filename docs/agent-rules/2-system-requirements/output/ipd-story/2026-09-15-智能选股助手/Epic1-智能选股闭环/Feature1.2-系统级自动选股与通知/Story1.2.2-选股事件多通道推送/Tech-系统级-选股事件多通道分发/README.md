# Tech-系统级-选股事件多通道分发

1、【技术故事】 - TL & 模块负责人

支撑 Story1.2.2（REQ-008）的事件分发链路：select_completed/select_failed 事件触发 → notify_service 按订阅策略（REQ-007）分发外部渠道（异步）→ 站内信必写（同步，REQ-009）→ 在线客户端 WebSocket 推送（REQ-010）。manual 通知归属用户、system 通知全员。

关联的系统需求编号：REQ-008；依赖 REQ-006/007/009/010。

2、【A/C验收条件】 - TL & 模块负责人

2.1 功能性验收条件

1、业务规则、边界：
- 内置事件 select_completed（含命中数/日期/前 N 条摘要，N 默认 5 可配置）、select_failed（含失败原因摘要）。
- manual 完成→通知归属用户；system 完成→通知全体用户。
- 站内信始终写入（无论外部渠道成败）；渠道未配置/发送失败不阻塞主流程。

2、系统功能约束：
- 外部渠道发送异步、不阻塞主流程；复用 notify_service 事件/策略/发送器（ch06 §6.2）。

3、实例化场景（正常场景和异常场景）：
- 正常：system 运行完成、策略含企微、A 配企微 → A 收到企微通知 + 站内信 + 在线 WS push；站内信落库 ≤1s。
- 异常：企微 webhook 不可达 → WARN 日志记录，站内信与 WS 正常送达；用户未配置渠道 → 仅站内信 + WS 无报错。

2.2 非功能性验收条件

1）性能分析：事件产生→站内信落库 ≤1s（PERF-07）；在线推送 ≤5s（PERF-05，配合 REQ-010）。
2）可靠性：双路互备、站内信兜底可回溯（REQ-008 非功能）。
3）可维护性：事件/接收范围/摘要配置环境变量化（N 默认 5 可配置，LOG-02）；发送失败留 WARN 日志（LOG-01）。
4）开放性：事件类型可扩展（select_* 后续扩展）；接口入 OpenAPI（OPN-01）。
5）安全性：按接收用户范围分发防串扰（SEC-01）；通知内容不含认证/密钥信息。
6）其他：可测试性——mock webhook + 独立事件触发，断言 webhook payload、站内信、WS 三路一致（TES-03/04）。

3、【依赖与风险】 - TL & 模块负责人

1、需求关联性，内部功能依赖，外部跨团队协作：依赖 REQ-006/007/009/010；webhook 三方可达性（尽力送达）。
2、技术风险、测试风险：外部 webhook 送达率不可控（低）→双路 + 站内信兜底。

4、【技术思路】 - TL & 模块负责人

1、技术如何实现，方案如何设计，指导开发：
   架构边界：notify 模块新增 select_* 事件定义与接收范围规则，复用既有事件/策略/发送器与节流代码路径（ch06 §6.2）；站内信写入走 REQ-009 通道。
2、技术方案：事件触发接入与外部渠道发送见服务级 Tech 文件；具体实现由开发负责人深化。
