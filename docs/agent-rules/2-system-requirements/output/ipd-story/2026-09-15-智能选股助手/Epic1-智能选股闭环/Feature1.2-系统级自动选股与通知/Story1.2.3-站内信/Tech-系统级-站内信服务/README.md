# Tech-系统级-站内信服务

1、【技术故事】 - TL & 模块负责人

支撑 Story1.2.3（REQ-009）的站内信链路：select_completed/select_failed 等事件写入 inbox_messages → 消息 Tab 列表/未读徽标/已读操作（接口 GET/PUT）→ 供 WebSocket 补齐（REQ-010）作为同步源。站内信为系统内可靠消息记录，仅本人可见。

关联的系统需求编号：REQ-009；依赖 REQ-008（写入）、REQ-010（补齐）、REQ-015（隔离）。

2、【A/C验收条件】 - TL & 模块负责人

2.1 功能性验收条件

1、业务规则、边界：
- inbox_messages 字段：id/user_id/type/run_id?/title/content/read_status/created_at。
- `GET /api/v1/messages` 按当前用户过滤 + 分页 + 返回未读数；`PUT /api/v1/messages/{id}/read` 标记已读。
- 事件覆盖 select_completed/select_failed（后续可扩展）；未读数徽标 100+ 显示"99+"。

2、系统功能约束：
- 消息为同步源，断线/离线期间经站内信持久化；读取强按 user_id 过滤。

3、实例化场景（正常场景和异常场景）：
- 正常：3 条消息 2 条未读 → 列表倒序展示、徽标未读数=2；标记已读后 read_status=read、未读数减 1。
- 异常：B 标记 A 的消息 → 拒绝返回无权限语义；id 不存在 → 404"消息不存在"；日本/越权不泄露消息存在性。

2.2 非功能性验收条件

1）性能分析：列表查询 p95 ≤1s（PERF-02）；写入与事件联动 ≤1s（PERF-07）。
2）可靠性：消息不丢（事件只要落库必可查）；站内信为补齐同步源（REL-04）。
3）可维护性：未读数/列表查询轻量分页；消息增长本期不自动清理（个人量级受控）。
4）开放接口：GET/PUT 消息接口入 OpenAPI（OPN-01）。
5）安全性：强 user_id 过滤（SEC-01）；越权返回无权限语义不泄露资源存在性。
6）其他：可测试性——接口/事件可靠构造消息，断言列表/未读/已读状态（TES-03）。

3、【依赖与风险】 - TL & 模块负责人

1、需求关联性，内部功能依赖，外部跨团队协作：依赖 REQ-008/010/015；不涉及外部团队。
2、技术风险、测试风险：消息无限增长（低）→本期不做自动清理，量级受控（个人工具）。

4、【技术思路】 - TL & 模块负责人

1、技术如何实现，方案如何设计，指导开发：
   架构边界：notify 模块站内信（含模型/存储/接口）复用既有 repositories 双实现；读取严格按当前用户过滤（REQ-015 统一用户作用域）。
2、技术方案：站内信模型与列表接口、已读与未读数接口见服务级 Tech 文件；具体实现由开发负责人深化。
