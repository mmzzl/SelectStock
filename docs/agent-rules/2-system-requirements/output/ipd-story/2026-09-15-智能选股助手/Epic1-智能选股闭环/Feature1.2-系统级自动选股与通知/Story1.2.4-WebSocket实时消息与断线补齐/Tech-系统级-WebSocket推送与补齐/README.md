# Tech-系统级-WebSocket推送与补齐

1、【技术故事】 - TL & 模块负责人

支撑 Story1.2.4（REQ-010）的实时链路：登录态连接 `/ws/notify`（token 鉴权、按 user_id 路由）→ 新站内信实时推送（latest_id/title/摘要）→ 安卓本地通知弹系统通知栏 → 断线重连按 since=latest_id 补齐。心跳保活 + 自动重连（指数退避，后台节流）。

关联的系统需求编号：REQ-010；依赖 REQ-008/009（消息源）、REQ-011（认证）。

2、【A/C验收条件】 - TL & 模块负责人

2.1 功能性验收条件

1、业务规则、边界：
- 连接：登录态 WebSocket 连接 `/ws/notify`，连接鉴权（token），按 user_id 路由，每用户独立连接不泄漏。
- 推送：新站内信产生实时推送（latest_id/title/摘要）；安卓经本地通知弹系统通知栏（买入/卖出信号）。
- 补齐：本地记录 latest_id，重连成功后按 since=latest_id 拉取站内信补齐缺口。
- 重连：心跳保活 + 自动重连（指数退避；后台节流）。

2、系统功能约束：
- WS 为推送/补齐 1 个端点；连接资源按用户隔离；不上厂商通道（ch06 §6.1）。

3、实例化场景（正常场景和异常场景）：
- 正常：在线且连接 → select_completed 产生站内信 → ≤5s 内收到推送、latest_id 前进、安卓弹通知栏。
- 异常：断线期间 3 条站内信 → 重连按 since 补齐 3 条 latest_id 收敛无漏无重；token 失效 → 断开并经 refresh 重连，刷新失败回登录；心跳超时 → 断开后指数退避重连（后台节流）无感恢复。

2.2 非功能性验收条件

1）性能分析：在线事件→客户端 ≤5s（PERF-05）。
2）可靠性：消息不丢（站内信为同步源）；连接管理不泄漏，每用户独立连接（REL-04）。
3）可维护性：断线/重连日志留痕（LOG-03）；心跳与重连间隔配置环境变量化（LOG-02）。
4）开放性：WS 端点接入文档；消息结构回退到站内信接口可查询（OPN-01）。
5）安全性：WS 连接鉴权（SEC-02）；按 user_id 路由防串扰（SEC-01）；token 不写日志（SEC-07）。
6）其他：可测试性——人工断开客户端连接构造断线，断言补齐消息与站内信一致、latest_id 收敛（TES-04）。

3、【依赖与风险】 - TL & 模块负责人

1、需求关联性，内部功能依赖，外部跨团队协作：依赖 REQ-008/009/011；不涉及外部团队。
2、技术风险、测试风险：连接管理/重连复杂度（中）→心跳 + 重连 + since 补齐（TR1 §1.2.5 风险 3 已评估）。
