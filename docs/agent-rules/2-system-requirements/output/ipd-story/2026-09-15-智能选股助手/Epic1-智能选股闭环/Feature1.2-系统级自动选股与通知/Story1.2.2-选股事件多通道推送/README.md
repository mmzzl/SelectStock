### 【Story】Story1.2.2-选股事件多通道推送 🔴

> 来源：REQ-008（P0）

【用户故事】⭐

作为个人投资者（使用者本人），我想要选股完成或失败时自动收到通知，以便无需手动查询即可掌握结果；系统对 webhook 失败有站内信兜底，保证消息不静默丢失。

【场景说明】⭐

针对选股事件的主动触达场景：select_completed（含命中数/日期/前 N 条摘要，N 默认 5 可配置）/ select_failed（含失败原因摘要）触发后，按订阅策略分发外部渠道 + 站内信必写 + WebSocket 实时推送。
**痛点背景**：无主动通知，信号需用户主动查询；诉求=事件触发即双路分发、站内信兜底。
- 来源：REQ-008（关联 ch02 场景1）

---

【A/C 验收条件】

一、功能性验收条件 ⭐

1、业务规则：
- 内置事件：select_completed（含命中数/日期/前 N 条摘要）、select_failed（含失败原因摘要）。
- 触发时机：manual 运行完成→通知归属用户；system 运行完成→通知全体用户。
- 分发路径：notify_service 按订阅策略发送外部渠道 + 站内信必写（双路，REQ-006/007）。
- 站内信始终写入（无论外部渠道成败）；渠道未配置/发送失败不阻塞主流程。
- 在线客户端经 WebSocket 实时推送（REQ-010）。

2、实例化场景描述：

   正常场景：completed 双路
   Given（前提条件）：system 运行完成，策略含企微，用户 A 配置了企微
   When（行为）：事件触发
   Then（结果）：A 收到企微通知 + 站内信 +（在线时）WS push；站内信落库 ≤1s

   异常场景：webhook 失败
   Given（前提条件）：企微 webhook 不可达
   When（行为）：事件触发
   Then（结果）：发送失败被记录（WARN 日志），站内信与 WS 正常送达

   异常场景：无渠道配置
   Given（前提条件）：用户未配置任何渠道渠道类型
   When（行为）：事件触发
   Then（结果）：仅站内信 + WS，无报错

   安全场景：manual 通知范围
   Given（前提条件）：用户 A 的 manual 运行完成
   When（行为）：事件触发
   Then（结果）：仅 A 收到通知，B 不受影响

   安全场景：system 全员通知
   Given（前提条件）：system 运行完成
   When（行为）：事件触发
   Then（结果）：全部用户均收到（各自按渠道）

   边界场景：命中摘要上限 / 连续事件
   Given（前提条件）：命中 100 条，摘要 N=5；或短时间内多个事件
   When（行为）：生成内容 / 分发
   Then（结果）：正文含前 5 条摘要 + 总计命中数；节流生效（REQ-007）、站内信逐条完整记录

【操作步骤】⭐

无需用户操作（事件自动触发）；用户可在消息 Tab 查看站内信或在第三方渠道（企微/钉钉/飞书/邮箱）接收通知。

【期望效果】⭐

事件触发即双路分发、站内信必写可回溯、外部渠道尽力送达、站内信落库 ≤1s（PERF-07）、在线推送 ≤5s（配合 REQ-010）。

【需求规格约束】🔲

通知内容模板（select_completed 前 N 条摘要，N 默认 5 可配置）。

二、非功能性验收条件 ⭐

【产品需求】

- 性能：事件产生→站内信落库 ≤1s（PERF-07）；外部渠道异步发送不阻塞主流程。
- 可靠性：双路互备、站内信兜底可回溯（REQ-008 非功能）。
- 可测试性：mock webhook + 独立事件触发，断言 webhook payload/站内信/WS 三路一致（TES-03/04）。

【安全需求】⭐ 必填（QS-007）

- 按接收用户范围分发，manual 只通知属主、防串扰（SEC-01）。
- 通知内容仅含选股元数据（code/name/signal/reason 等），不含认证或密钥信息。
- token 不写日志（SEC-07）。

【海外合规】🔲

不涉及（个人自用国内工具，QS-006 裁剪）。

【依赖与风险】⭐

1、需求关联性，内部功能依赖：依赖 REQ-006（渠道）、REQ-007（策略）、REQ-009（站内信）、REQ-010（WS）。
2、技术风险、测试风险：外部 webhook 送达率不可控（低）→双路 + 站内信兜底。
3、跨团队协作（沟通/确认/附件）：三方 webhook 可达性（尽力送达，非 SLA）。
