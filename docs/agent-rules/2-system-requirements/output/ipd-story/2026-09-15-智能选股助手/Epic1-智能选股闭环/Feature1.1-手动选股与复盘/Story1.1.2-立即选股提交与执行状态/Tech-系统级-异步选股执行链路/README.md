# Tech-系统级-异步选股执行链路

1、【技术故事】 - TL & 模块负责人

支撑 Story1.1.2（REQ-002）的端到端选股执行链路：客户端提交 → `POST /select/run` 返回 run_id（≤2s）→ 后端异步代理插件 `POST /api/selector/run` → 状态机 running/success/failed → 完成后接入快照落库（REQ-003）与事件通知（REQ-008）。

关联的系统需求编号：REQ-002；与 REQ-016（治理）、REQ-003（落库）、REQ-008（通知）协同。

2、【A/C验收条件】 - TL & 模块负责人

2.1 功能性验收条件

1、业务规则、边界：
- `POST /select/run` 入参勾选策略列表，≤2s（p95）返回 run_id；提交为空返回 400。
- 异步执行，前/后端不轮询阻塞；manual 运行 owner 由服务端生成。
- 状态可查询（running/success/failed），同一时刻全局仅 1 个运行中任务（并发校验转交 REQ-016）。

2、系统功能约束：
- 仅登录用户可提交（401）；未登录提交不创建任务。

3、实例化场景（正常场景和异常场景）：
- 正常：已登录、勾选策略、无运行中任务 → 提交 → ≤2s 返回 run_id → 插件返回后置 success → 结果 Tab 可见明细。
- 异常：已有 running 任务再次提交 → 拒绝并提示"已有选股任务执行中"；插件失败 → 重试耗尽后置 failed 并触发 select_failed。

2.2 非功能性验收条件

1）性能分析：提交接口 p95 ≤2s（PERF-03）；任务 30 分钟内完成（PERF-04）。
2）可靠性：异步不阻塞；长任务超时/重试兜底依赖 REQ-016（REL-02/03）。
3）可维护性：status/error 全量落库可追溯（LOG-03）；并发/超时配置环境变量化（LOG-02）。
4）开放性：`POST /select/run`、状态查询接口入 OpenAPI 文档（OPN-01）。
5）安全性：登录鉴权；归属服务端生成防覆盖（SEC-01）；token 不写日志（SEC-07）。
6）其他：可测试性——mock 插件注入正常/超时/失败三类响应断言状态与耗时（TES-02）。

3、【依赖与风险】 - TL & 模块负责人

1、需求关联性，内部功能依赖，外部跨团队协作：REQ-001（策略）、REQ-003（落库）、REQ-008（事件）、REQ-016（治理）；插件 run 接口（耗时任务）。
2、技术风险、测试风险：长任务失败无兜底（中）→超时 + 重试 + select_failed 通知（P1-001 已纳入 REQ-016）。

4、【技术思路】 - TL & 模块负责人

1、技术如何实现，方案如何设计，指导开发：
   架构边界：select 模块新增提交/状态查询 API 与状态机 service，异步执行不阻塞请求线程（ch06 §6.2）；复用既有日志与 repositories 基建。
2、技术方案：提交接口 + 状态机 service + 客户端立即选股交互（服务级 Tech 详见下方文件）；具体实现由开发负责人深化。
