### 【Story】Story1.1.3-任务执行治理 🟡

> 来源：REQ-016（P1）

【用户故事】⭐

作为个人投资者（使用者本人），我想要选股任务不会无限转圈、失败有兜底与通知，以便选股执行可靠、失败可感知。

【场景说明】⭐

针对全部选股场景的运行治理：长任务失败无重试、失败不可感知（TR1 P1-001 问题纳入）；诉求=单并发、30 分钟超时、失败重试 3 次参数退避、失败通知。
**痛点背景**：长任务失败无重试与用户可感知失败提示，已纳入本版本需求池（REQ-016）。
- 来源：REQ-016（关联 ch02 场景2）

---

【A/C 验收条件】

一、功能性验收条件 ⭐

1、业务规则：
- 单并发：同一时刻全局仅 1 个运行中选股任务，超额提交被拒（REQ-002 并发场景）。
- 超时：任务运行超 30 分钟 → 状态置 failed、记录 error（恰好 30 分钟不算超时）。
- 重试：插件调用失败自动重试（默认 3 次，指数退避含抖动）→ 仍失败置 failed。
- 失败通知：触发 select_failed 事件（REQ-008 双路分发）。
- 手动触发：失败后允许用户再次手动提交（不自动重跑重试耗尽的任务）。

2、实例化场景描述：

   正常场景：单并发与并发位释放
   Given（前提条件）：1 个 running 任务
   When（行为）：再提交 / 任务完成后再次提交
   Then（结果）：running 期间拒绝并提示"已有选股任务执行中"；完成后允许提交、新任务进入 running

   异常场景：超时兜底
   Given（前提条件）：任务运行 30 分钟未完成
   When（行为）：超时检查触发
   Then（结果）：置 failed、记录 error、触发 select_failed 通知；无僵尸任务

   异常场景：重试耗尽
   Given（前提条件）：插件连续失败 3 次
   When（行为）：重试
   Then（结果）：指数退避重试（含抖动）耗尽后置 failed + 通知

   安全场景：终态幂等
   Given（前提条件）：任务已 failed/success
   When（行为）：重复终态写入/重复事件触发
   Then（结果）：不产生重复状态变更与重复通知

   安全场景：手工重跑
   Given（前提条件）：任务 failed
   When（行为）：用户再次手动提交
   Then（结果）：允许（新建 run），不自动重试已耗尽任务

   边界场景：0 秒完成 / 超时临界值
   Given（前提条件）：插件瞬时返回或耗时恰好 30 分钟
   When（行为）：运行/超时判断
   Then（结果）：状态流转正常、duration_ms 记录实际耗时；恰 30 分钟不算超时

【操作步骤】⭐

无需用户主动操作（系统兜底自动执行）；用户可感知结果 Tab 的失败原因，并可在失败后再次手动提交选股。

【期望效果】⭐

无僵尸任务（超时兜底）、失败可感知（通知 + 结果 Tab 原因）、并发位正确释放、重试与终态写入幂等。

【需求规格约束】🔲

不涉及（系统级治理逻辑，无专属交互页面；失败原因展示复用结果 Tab）。

二、非功能性验收条件 ⭐

【产品需求】

- 性能：选股任务 30 分钟内完成并落库（PERF-04）；超时检测不依赖阻塞轮询外挂（REQ-016 非功能）。
- 可靠性：失败重试 3 次指数退避（REL-02）；长任务超时兜底无僵尸任务（REL-03）。
- 可扩展性：全局并发位单任务（SCA-02）。
- 可测试性：mock 插件可注入延迟/连续失败，断言状态时序、重试次数、退避间隔（TES-02）。

【安全需求】⭐ 必填（QS-007）

- 终态写入幂等、重复事件不产生重复通知（SEC-01 语义 + LOG-03 可追溯）。
- select_runs 全量留痕（含 error），供追溯统计。
- token 不写日志、不明文（SEC-07）。

【海外合规】🔲

不涉及（个人自用国内工具，QS-006 裁剪）。
