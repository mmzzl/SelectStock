# 2. 关键应用场景

> 功能需求（§3）中的每条 REQ 均关联本章场景。场景已在上游 TR1 中确认。

## 2.1 场景1：下班路上查看今日选股信号（系统级自动选股+通知）

| 项目 | 说明 |
|---|---|
| 场景描述 | 每日收盘后外部调度服务自动执行选股，命中信号落库并通知使用者 |
| 用户角色 | 个人投资者（使用者本人） |
| 使用方式 | 手机 App 或 PC 浏览器；被动接收通知 + 主动查看 |
| 原型/交互依据（如适用） | 消息 Tab + 结果 Tab 交互稿（待交互设计阶段产出） |
| 操作流程 | 1. 外部调度在 15:05 调用选股插件 → 2. 导入后端（系统级运行）落库 → 3. 通过 WebSocket/站内信推送给全体用户 → 4. 使用者收到通知（在线即时 / 离线重连补齐）→ 5. 打开消息或结果 Tab 查看命中明细 |
| 异常分支 | 调度失败/导入失败：无新运行、无推送，下次调度重试（REQ-005 异常场景）；webhook 渠道不可达：站内信照常送达（REQ-008 异常流程场景 1）；离线期间消息：重连按 since 补齐（REQ-010 断线补齐） |
| 期望目标 | 事件→客户端通知 ≤ 5s（在线，PERF-05）；离线由站内信补齐；历史按自然日可回看 |
| 业务价值 | 不再依赖 SSH/命令行，定时选股自动执行、信号主动送达 |

**关联需求：** REQ-003/004/005/008/009/010

## 2.2 场景2：临时手动选股与复盘

| 项目 | 说明 |
|---|---|
| 场景描述 | 使用者想换策略立即选一次，并在之后回看历史 |
| 用户角色 | 个人投资者（使用者本人） |
| 使用方式 | App 选股 Tab 勾选策略 → 立即选股 |
| 原型/交互依据（如适用） | 选股 Tab + 结果 Tab 交互稿 |
| 操作流程 | 1. 打开选股 Tab → 2. 勾选 1 个或多个策略（≤3 步）→ 3. 点击"立即选股" → 4. ≤2s 内获得 run_id，任务异步执行 → 5. 完成后结果 Tab 展示该次命中明细（本次归属本人，仅本人可见） |
| 异常分支 | 已有运行中任务：提交被拒提示稍后再试（REQ-002 异常流程场景 1）；插件异常：重试 3 次后失败置 failed 并通知（REQ-016）；任务超 30 分钟：置 failed（REQ-016 超时兜底） |
| 期望目标 | 提交响应 ≤ 2s；单任务并发（同一时刻仅 1 个运行中任务）；完成即可查看 |
| 业务价值 | 临时决策即时可查，结果持久化支持复盘 |

**关联需求：** REQ-001/002/003/004/012/016

## 2.3 场景3：通知配置与渠道验证

| 项目 | 说明 |
|---|---|
| 场景描述 | 使用者配置企微/钉钉/飞书/邮箱渠道并设置订阅策略，检验通知是否到达 |
| 用户角色 | 个人投资者（使用者本人） |
| 使用方式 | 设置 Tab 维护渠道与策略 |
| 原型/交互依据（如适用） | 设置 Tab 交互稿 |
| 操作流程 | 1. 新增渠道（选择类型、填 webhook、≤3 步）→ 2. 点击"测试发送" → 3. 目标收到测试消息 → 4. 编辑全局订阅策略（事件→渠道类型→节流间隔）→ 5. 保存 |
| 异常分支 | webhook 无效：测试发送反馈失败及原因，不阻塞保存（REQ-006 异常流程场景 1）；渠道未配置的渠道类型：发送静默跳过，站内信兜底（REQ-007 异常流程场景 1） |
| 期望目标 | 渠道新建并测试 ≤3 步；渠道数据仅本人可见；策略全局生效 |
| 业务价值 | 通知链路可视化、可验证，不因配置错误静默丢失 |

**关联需求：** REQ-006/007/008/012/017

## 2.4 场景4：换新手机后的安装与升级

| 项目 | 说明 |
|---|---|
| 场景描述 | 使用者在新 Android 手机上安装 App，或收到新版本推送 |
| 用户角色 | 个人投资者（使用者本人） |
| 使用方式 | 打开 App 时自动检查版本 |
| 原型/交互依据（如适用） | 版本升级弹窗交互稿 |
| 操作流程 | 1. 安装旧版 App 后启动 → 2. 版本检查发现新版 → 3. 可选更新弹"以后再说"/"立即升级"；强制更新弹窗不可跳过 → 4. 点立即升级 → 下载 APK（进度条）→ 校验 MD5 → 引导"安装未知应用"授权 → 系统安装 → 5. 新版本启动成功 |
| 异常分支 | 下载中断：提示失败可重试（REQ-014 异常流程场景 2）；MD5 不一致：拒绝安装并删除残留（REQ-014 异常流程场景 1）；版本接口不可达：静默放行不阻塞使用（REQ-014 边界场景 2） |
| 期望目标 | 启动即检查；下载失败可重试；MD5 不一致不安装；强制更新完成前不可用 |
| 业务价值 | 修复与功能迭代可交付到手机，无人工拷贝 |

**关联需求：** REQ-014/017

## 2.5 场景5：多账号下的隔离与会话

| 项目 | 说明 |
|---|---|
| 场景描述 | 使用者本人有一个主账号与一个测试账号（均来自 sys_users），两个账号数据互不可见 |
| 用户角色 | 使用者本人 / 多账号用户 |
| 使用方式 | 登录不同账号使用 |
| 原型/交互依据（如适用） | 登录页 + 设置 Tab 交互稿 |
| 操作流程 | 1. 账号 A 登录 → 手动选股产生运行 r1 → 2. 退出，账号 B 登录 → 查看历史：不含 r1；消息/渠道亦为空 → 3. 外部调度导入的系统级运行 r2：A、B 均可见 |
| 异常分支 | 越权访问（B 携 A 的资源 id）：拒绝并返回无权限语义（REQ-015 异常流程场景）；登录失败/锁定/到期：不进入，展示后端原样语义（REQ-011 异常流程场景） |
| 期望目标 | 私有数据不跨账号泄露；系统级数据全员可见；越权请求返回无权限语义 |
| 业务价值 | 账号间数据隔离可靠，测试/正式互不干扰 |

**关联需求：** REQ-011/013/015

## 2.6 场景6：持仓录入与定时诊断（持仓×插件统一判定）

| 项目 | 说明 |
|---|---|
| 场景描述 | 使用者录入当前持仓，每日收盘后外部调度把持仓发给选股插件统一判定买卖/加仓，收益快照落库并通知属主 |
| 用户角色 | 个人投资者（使用者本人） |
| 使用方式 | 手机 App 或 PC 浏览器；被动接收诊断通知 + 主动回看 |
| 原型/交互依据（如适用） | 持仓页/持仓诊断历史交互稿（待交互设计阶段产出） |
| 操作流程 | 1. 使用者录入持仓（手动或导入券商 CSV）→ 2. 外部调度在收盘后调用诊断入口 → 3. 后端按用户取持仓代理插件 `POST /api/portfolio/analyze` → 4. 插件统一判定卖出/加仓并返回收益快照 → 5. 结果落库 + 属主通知（外部渠道/站内信/WS）→ 6. 使用者回看历史诊断 |
| 异常分支 | 插件不可用：重试 3 次后 failed + portfolio_diag_failed 通知（REQ-019）；用户无持仓：跳过不诊断（REQ-019 边界）；webhook 失败：站内信兜底（REQ-021）；越权访问他人持仓/诊断：拒绝（REQ-015） |
| 期望目标 | 诊断由插件统一判定（与回测判定同源）；收益快照落库回看；结果仅属主可达 |
| 业务价值 | 持仓买卖/加仓判断从"人肉比对选股信号"变为"插件统一判定"，收益演进可回溯 |

**关联需求：** REQ-007/009/010/015/016/018/019/020/021
