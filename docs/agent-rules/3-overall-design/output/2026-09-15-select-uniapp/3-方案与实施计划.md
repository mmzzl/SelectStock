# 持仓诊断闭环 · 方案与实施计划（唯一事实源之三）

> 本文件 = **接口契约 + DB 双表 + 边界 + TDD 拆分**，是本迭代唯一事实源。编码时只认本文件与《1-需求清单》《2-红线契约》；`3-overall-design/output/…/trd/` 仅作历史存档，**不再作同步对象**。
> 关联 REQ：018/019/020/021（均 P0 新增）。

## 1. 外部调度 → 后端的诊断批次（外部调度触发，RECALL 单飞位）

| 项 | 契约 |
|---|---|
| 触发方 | 外部独立调度服务（与定时选股 RECALL-05 共用同一外部调度，**不进 FastAPI 定时器**） |
| 入口 | `POST /api/external/portfolio/diag`（鉴权：令牌或既有外部调度凭证；幂等键 = `portfolio_diag:{user_id}:{natural_day}`） |
| 幂等 | 相同幂等键重复触发 → 返回既有 run_id（不重复建 run，R2-2/REL-08） |
| 入参 | `{ "user_id": "{uid}", "natural_day": "2026-09-15" }`（诊断按日执行；收益/市值为该 natural_day 场景） |
| 出参 | `{ "run_id": "{run_id}", "status": "running|queued" }` + `Location` 头指 `GET /api/portfolio/diag/{run_id}` |
| 单飞 | 全局同一时刻仅 1 个 diagnostic 运行中（REQ-016 单并发扩展至持仓诊断；`diag_runs` 行级锁） |

## 2. 后端 → 插件（代理，R2-1/R1 判定全收敛插件）

| 项 | 契约 |
|---|---|
| 入口 | `POST /api/portfolio/analyze`（后端对插件的唯一诊断代理口，**复用既有的 notify_service 状态机 + 外部调度**） |
| 入参 | `{ "user_id": "{uid}", "holdings": [ {code,name,quantity,cost_price} ], "natural_day": "{day}" }`，插件**必须**返回 `action`（sell/hold/add）判定 |
| 出参 | `{ "run_id": "{run_id}", "results": [ {code, action, action_reason, latest_price, holding_pnl, pnl_pct, suggestion} ], "summary": {...}}` —— **收益/市值/收益均由插件计算**（R1-4 收益来自插件附加每只 `latest_price`、`holding_pnl`、`pnl_pct`） |
| 边界 | 后端零计算判断（R1-1）；插件不可用 → 指数退避重试 3 次 → 置 `failed` + `portfolio_diag_failed` 双路通知（REL-07/R2-2） |
| 幂等/重放 | 同一 diagnostic `run_id` 重放不重复建 run/明细（REL-08/R2-2） |

## 3. DB 双表落库（REQ-020）

| 表 | 用途 | 关键列 | 约束 |
|---|---|---|---|
| `portfolio_diag_runs` | 1 次诊断 run 头 | id/batch_id/user_id/natural_day/status/held_code_count/action_count/total_market_value/total_pnl/plugin_time_ms/error/created_at | 幂等键 `(user_id, natural_day, batch_id)`；status ∈ running/failed/completed |
| `portfolio_diag_results` | run 明细 | id/run_id/code/name/action/action_reason/latest_price/quantity/holding_pnl/pnl_pct/suggestion | `(run_id, code)` 唯一 |

> 收益/市值统一由插件给出（R1-1/1-4），后端只落库不计算（R1-2）。

## 4. 归属与隔离（REQ-018/019/020/021）

| 数据 | 隔离方式 | 红线 |
|---|---|---|
| 持仓（holdings） | user_id 隔离，属主独占 | R1-2（隔离边界） |
| 诊断 run+明细 | user_id 隔离 | R1-2 |
| 收益快照 | 随诊断结果透传（插件计算） | R1-1 |
| 诊断事件 | `portfolio_diag_confirmed`/`portfolio_diag_failed` 双路通知，属主可见 | REL-04/07 （复用事件框架） |

## 5. 实施计划（TDD 逐模块 + 自测闭环）

> 本项目 TDD 纪律（T-深）：**先红线 → 契约 → 测试 → 实现**。下表为任务拆分，每任务先写 red（FAIL）→ 实现 → 绿（PASS），全程自测闭环，逐模块验收后再进入下一模块。

| 阶段 | 任务 | 详细工作 | 验收基准（红线锚点） |
|---|---|---|---|
| M0 | 契约锚定 | 以本文件 + REQ 清单为准，建立"红线→REQ→TC/测试"跟踪表（复用 ch03/04 章节索引，标注 REQ-018~021 新增行） | R1/R2 全锚定，无漂移 |
| M1 | 插件 analyze 契约+DB 双表 | 后端新增 `POST /api/portfolio/analyze`、`portfolio_diag_runs/results` 双表、幂等键+隔离索引 | R2-î 幂等、R1 判定零后端计算 |
| M2 | 插件 analyze 判定 | 插件实现 analyze（判 sell/hold/add + 收益快照，行情来源复用既有行情链路） | R1-1/1-4 插件收益计算 + 判定收敛 |
| M3 | 外部调度诊断批次 | 外部调度 `POST /api/external/portfolio/diag`、幂等批次键、单飞 | R2-2/RES-07 重试 3 次退避、failed |
| M4 | 事件双路通知 | 复用 notify_service 双路（WS+站内信），属主隔离、失败兜底 | REL-04/07 属主收到、非属主不可见 |
| M5 | 客户端持仓/诊断 Tab | UniApp 持仓录入+导入、诊断历史回看、壳层隔离 | REQ-012 守卫 + REQ-018~021 |
| M6 | 端到端闭环自检 | 插件 mock + 外部调度驱动全链路（导入→调度→诊断→快照→通知→回看） | 全 GWT 通过、红线无违约 |

## 6. 自检与红线挂钩

- 每个 M1~M6 完成后运行：`pytest`（新增持仓/诊断用例）→ 插桩 analyze 自测 → 越权矩阵（REQ-015）→ DFX 余量检查。
- 出现违约 → 回退对应模块重跑（R2-2/R5 纪律）。
- 逐模块交给使用者（本人）评审后再进入下一模块（自测闭环 + 评审检查点）。
