## 1.2.5. 特性技术方案选型

### 1.2.5.1. 选股代理执行模型的选型

#### 1.2.5.1.1. 业务场景关键问题及技术特征

- 长任务：插件 `/api/selector/run` 同步阻塞，全市场选股分钟级。
- 并发互斥：手动（用户）与外部调度（system）可能同时触发，插件单进程无内部并发保护，双任务并发会拉爆线程池 + 数据源风控 + GIL 竞争。
- 可恢复性：进程重启 / 多 worker 下单飞与任务状态必须不失效。
- 排队可见性：多人并发时后续请求须得到 `in_progress`/`queued` 明确反馈，不允许无声等待。

#### 1.2.5.1.2. 业务规格要求及约束

- 提交响应 ≤2s 返回 run_id（PERF-03）；任务 30 分钟内完成（PERF-04）；失败重试 3 次指数退避（REL-02）；超时兜底置 failed（REL-03）。
- 不引入常驻外部服务（无 Redis/Celery/RabbitMQ）；单机部署；单 worker 硬约束。
- 幂等导入（REL-06）；（POS.）`external_run_id` 唯一。

#### 1.2.5.1.3. 方案1：进程内 asyncio 后台任务 + DB 原子单飞锁

- 提交接口立即返回 `run_id`；`asyncio.create_task` 执行（async httpx 调插件，超时 60~300s 可配）。
- 单飞：`UPDATE select_runs SET status=running WHERE id=? AND status IN (pending, interrupted)` 影响行数==1 才继续（DB 级，跨进程有效）。
- 失败重试 3 次指数退避+抖动；超时 30 分钟置 failed。
- 启动时 `UPDATE select_runs SET status=interrupted WHERE status=running` 自愈僵尸任务。
- 部署硬约束 `uvicorn --workers 1`（配合 WS 连接表同进程）。
- 排队语义：运行中→`in_progress`；创建 pending 未执行→`queued`；完成后 WS 推送"选股完成"事件。

#### 1.2.5.1.4. 方案2：引入外部任务队列（Celery + Redis）

- 提交→入队→worker 消费→触发插件→回写。
- 分布式可靠、故障转移、可横向扩展。

#### 1.2.5.1.5. 方案选型决策

| 评估准则（基于业务关键技术特征维度提炼） | 权重 | 评估方法 | 方案1: asyncio+DB单飞 | 方案2: Celery+Redis | 给分依据说明 |
| --- | --- | --- | --- | --- | --- |
| 部署复杂度（新增常驻服务数） | 25% | 新增进程数 | 5 / 1.25 | 2 / 0.50 | 方案1 零新增服务；方案2 引入 Redis+borker-worker |
| 单飞/互斥可靠性 | 30% | 锁跨进程有效性 | 4 / 1.20 | 5 / 1.50 | DB 原子更新已跨进程有效；队列天然串行更优 |
| 任务可恢复性（重启/崩溃） | 20% | 僵尸任务处理 | 4 / 0.80 | 5 / 1.00 | 方案1 启动自愈；方案2 worker ack 原生支持 |
| 与事件循环/WS 集成成本 | 15% | 与既有 asyncio 栈契合度 | 5 / 0.75 | 3 / 0.45 | 方案1 原生同进程推送连接表 |
| 运维与排障成本 | 10% | 排障面 | 4 / 0.40 | 2 / 0.20 | 单进程日志即可定位 |
| 最终得分（满分5分） | | | **4.40** | 3.65 | 方案1 在个人单机场景综合最优 |

**选型决策：**

| 备选方案名称 | 本方案的优点 | 本方案的风险和缺点 | 最终选择 |
| --- | --- | --- | --- |
| 方案1: 进程内 asyncio + DB 单飞 | 零新服务；与 asyncio/WS 同栈；DB 锁跨进程有效；启动自愈 | 多 worker 不可用（已硬约束单 worker）；任务不落队列，故障转移靠 retry+自愈 | **✓ 采用** |
| 方案2: Celery + Redis | 分布式可靠、横向扩展、原生重试 | 新增 2 个常驻服务，个人工具过重；与既有 asyncio 栈割裂 | — |

#### 1.2.5.1.6. 方案对业务的约束

- **部署约束**：后端必须 `--workers 1`（文档化，多 worker 下 WS 连接表与单飞降级）。
- **体验约束**：并发选股任务全局 ≤1，超出的请求获 `in_progress`/`queued` + 完成通知（不静默等待）。
- **互斥范围**：`POST /select/run`（manual）与 `POST /select/import`（system）共用同一把 DB 单飞锁，覆盖外部调度入口。

### 1.2.5.2. 实时推送（WebSocket）通道的选型

#### 1.2.5.2.1. 业务场景关键问题及技术特征

- 实时性：事件→客户端 ≤5s（PERF-05）；同时站内信落库 ≤1s（PERF-07）。
- 可靠性：在线实时推 + 离线断线补齐（REL-04）；消息不丢以"落库为可信源"。
- 规模：单用户/少量并发连接（≤10），单机。

#### 1.2.5.2.2. 业务规格要求及约束

- 鉴权：连接复用统一认证；**首帧鉴权**（连接建立后第一条鉴权消息，60s 未鉴权断开），token 不进 URL/日志（SEC-07/LOG-06）。
- 断线补齐：客户端重连 + 每条消息携带 `latest_inbox_id` 增量对齐。
- 心跳保活：服务端/客户端 ping-pong，超时清理死连接。

#### 1.2.5.2.3. 方案1：FastAPI 原生 WebSocket + 内存连接表

- `@app.websocket("/ws/notify")`；connect 后先收帧鉴权（JWTPayload→user_id）；失败返回错误码后关闭。
- `WsManager`：`{user_id: set[WebSocket]}` 单播广播；发送失败移除并交由站内信兜底。
- 与 asyncio 后台任务同进程协作（选型 §1.2.5.1 互配）。

#### 1.2.5.2.4. 方案2：消息中间件（Redis Pub/Sub / MQ）分发

- 事件发布到中间件，WS 网关订阅后推给连接。
- 多 worker/多节点可行，但引入 Redis；单机个人场景收益为负。

#### 1.2.5.2.5. 方案选型决策

| 评估准则 | 权重 | 评估方法 | 方案1: FastAPI 原生 WS | 方案2: Redis/MQ 分发 | 给分依据说明 |
| --- | --- | --- | --- | --- | --- |
| 部署复杂度 | 25% | 新增服务数 | 5 / 1.25 | 1 / 0.25 | 方案1 零新增 |
| 与单 worker 架构契合度 | 30% | 连接路由一致性 | 5 / 1.50 | 4 / 1.20 | 单 worker 下原生即一致；中间件仍需网关进程 |
| 实现成本 | 20% | 代码量/学习成本 | 4 / 0.80 | 3 / 0.60 | 原生 API 成熟 |
| 断线/心跳/对齐机制复杂度 | 15% | 与站内信兜底配合 | 4 / 0.60 | 4 / 0.60 | 两方案均需客户端补拉协议 |
| 未来多节点演进 | 10% | 横向扩展能力 | 2 / 0.20 | 5 / 0.50 | 仅当长期多机才有价值 |
| 最终得分（满分5分） | | | **4.35** | 3.15 | 方案1 与上一选型互配、架构最简 |

**选型决策：**

| 备选方案名称 | 本方案的优点 | 本方案的风险和缺点 | 最终选择 |
| --- | --- | --- | --- |
| 方案1: FastAPI 原生 WS + 内存连接表 | 零服务；首帧鉴权简单可控；与任务进程同栈 | 单 worker 约束；进程重启连接全断（客户端退避重连+补齐兜底） | **✓ 采用** |
| 方案2: Redis/MQ 分发 | 多节点可扩展 | 新增服务；个人单机场景复杂化 | — |

#### 1.2.5.2.6. 方案对业务的约束

- **可靠性约束**：一切以站内信（落库）为可信源，WS 仅加速在线感知；客户端必须实现重连退避 + since/latest_inbox_id 对齐协议。
- **安全约束**：首帧鉴权，非法连接 60s 内关闭；令牌仅内存持有。

### 1.2.5.3. 快照/站内信/运行日志存储的选型

#### 1.2.5.3.1. 业务场景关键问题及技术特征

- 数据形态：结构化小数据（选股快照单次 ≤ 数百条、站内信、运行日志），读多写少，强一致性要求低（个人工具）。
- 关系：run→results 1:N；user→inbox 1:N；需自然日分组查询、分页、按 run 聚合。
- 存量：后端已支持 `db_backend=sqlite|mongodb` 双开关，默认 sqlite（`sqlite+aiosqlite`，`data/app.db`）。

#### 1.2.5.3.2. 业务规格要求及约束

- 查询接口 p95≤1s（PERF-02）；导入 500 条 ≤5s（PERF-06）；站内信落库 ≤1s（PERF-07）。
- 日志保留 ≥90 天；站内信保留 ≥180 天。
- 并发写：WS/任务/API 并发；需 WAL + busy_timeout + 单仓储串行化。

#### 1.2.5.3.3. 方案1：SQLite 新表（复用既有 app.db）

- 新表 `select_runs` / `select_results` / `inbox_msgs` / `user_channels` / `app_versions` / `select_run_logs`。
- WAL 模式 + `busy_timeout`（如 5000ms）；写走单一仓储实例排队；唯一约束：`select_runs.external_run_id`、`select_results(run_id,code)`、`user_channels(user_id,key)`。

#### 1.2.5.3.4. 方案2：MongoDB

- 新建 DB 集合承载同结构文档；利用既有 mongodb 开关。

#### 1.2.5.3.5. 方案选型决策

### 1.2.5.4. 通知渠道多用户隔离的选型

#### 1.2.5.4.1. 业务场景关键问题及技术特征

- 既有渠道配置为全局 JSON（`notify_channels.json`，单租户）；REQ-015 要求渠道为私有数据（仅属主可见）。
- 密钥 AES-GCM 加密落盘、不明文返回（SEC-03）必须保留。
- 订阅策略保持全局共享（REQ-007），用户各配自己的渠道（REQ-006）。
- 推送时 channel_key 需从"用户所属渠道"解析（既有发送器从全局 JSON 取）。

#### 1.2.5.4.2. 业务规格要求及约束

- 越权访问返回无权限语义（SEC-01）；破坏性删除二次确认（REL-05）。
- 既有 `GET|POST|PUT|DELETE /notify/channels` 接口按需升级为"我的渠道"语义，且不破坏既有全局渠道（兼容与回归）。

#### 1.2.5.4.3. 方案1：新增 DB 表 `user_channels`

- 字段：id, user_id, type(wecom|dingtalk|feishu|email), key, name, webhook_url, secret(AES-GCM), host/port/use_ssl/username/password/from_email/from_name, enabled, created_at。
- 唯一约束 (user_id, key)；查询/写入走 SQL 仓储（幂等 upsert）。
- 发送链路：`send_event(user_id, event, ...)` → 策略选渠道类型 → 用户渠道解析（DB）→ 既有 webhook/SMTP 发送器执行。
- 节流 state 键 = `user_id:channel_key:event`，文件写锁或挪 SQLite。

#### 1.2.5.4.4. 方案2：extend `notify_channels.json` 增加 user_id 字段

- 同一 JSON 同时承载全局与用户渠道（user_id 空=全局）。
- 改动小，但混存私有+全局数据，越权/加密/清理/锁竞争劣化。

#### 1.2.5.4.5. 方案选型决策

| 评估准则 | 权重 | 评估方法 | 方案1: DB 表 user_channels | 方案2: JSON 扩展 user_id | 给分依据说明 |
| --- | --- | --- | --- | --- | --- |
| 数据隔离/越权防护 | 35% | 私有数据边界清晰度 | 5 / 1.75 | 2 / 0.70 | DB 按 user_id WHERE 天然隔离；混存 JSON 易漏过滤 |
| 密钥安全（AES-GCM 落盘） | 25% | 加密路径统一 | 5 / 1.25 | 4 / 1.00 | 两方案均复用 core.security；DB 留密文列更可控 |
| 并发写安全 | 20% | 多用户同时写 | 5 / 1.00 | 2 / 0.40 | JSON 读改写需文件锁；DB 事务天然 |
| 既有兼容与回归成本 | 20% | 通知 API 影响面 | 3 / 0.60 | 4 / 0.80 | 方案2 结构性改动更小，但语义污染 |
| 最终得分（满分5分） | | | **4.60** | 2.90 | 隔离与安全维度压倒性倾斜方案1 |

**选型决策：**

| 备选方案名称 | 本方案的优点 | 本方案的风险和缺点 | 最终选择 |
| --- | --- | --- | --- |
| 方案1: DB 表 user_channels | 隔离清晰；密钥加密列统一；事务写安全；查询表达式成熟 | 需改造既有通知 API/发送链路为双源解析，完整回归既有通知功能 | **✓ 采用** |
| 方案2: JSON 扩展 user_id | 改动面小 | 私有数据混存、越权风险、多用户写锁竞争 | — |

#### 1.2.5.4.6. 方案对业务的约束

- **兼容约束**：既有全局渠道（JSON）保留为系统级通道；用户渠道 API 升级为"我的渠道"语义；`send_event` 双源解析（优先级：用户 DB → 全局 JSON），专项回归 RT/ST 既有通知用例。

### 1.2.5.5. APK 版本托管与下载的选型

#### 1.2.5.5.1. 业务场景关键问题及技术特征

- 小规模整包分发：Android APK（十几~几十 MB），单用户/极少量下载，无需 CDN。
- 完整性：下载后 MD5 校验，不一致拒绝安装（SEC-04）。
- 强制升级策略：force=0/1；校验失败提供"暂仍使用旧版"出口（防死循环）。

#### 1.2.5.5.2. 业务规格要求及约束

- 客户端 uni.downloadFile 支持进度条；`GET /api/v1/app/version` 返回最新版本 + force + md5 + size + 下载地址。
- 下载需断点/Range 支持（uvicorn 静态挂载原生支持）。

#### 1.2.5.5.3. 方案1：后端静态文件托管（`data/apk/`）

- `app_versions` 表记录 version_code/version_name/force/desc/apk_path/md5/size/enabled/created_at。
- FastAPI `StaticFiles` 挂载 `/static/apk/`；下载接口 + MD5 头信息。

#### 1.2.5.5.4. 方案2：对象存储（MinIO/OSS）

- 独立对象存储托管 APK + 预签名 URL。

#### 1.2.5.5.5. 方案选型决策

| 评估准则 | 权重 | 评估方法 | 方案1: 静态文件 | 方案2: 对象存储 | 给分依据说明 |
| --- | --- | --- | --- | --- | --- |
| 部署复杂度 | 40% | 新增服务 | 5 / 2.00 | 1 / 0.40 | 静态托管零成本 |
| 完整性保障 | 30% | MD5 校验链路 | 4 / 1.20 | 5 / 1.50 | 两方案均可；对象存储链路更多需透传 |
| 带宽/并发扩展 | 20% | 大文件下载扩展 | 2 / 0.40 | 5 / 1.00 | 仅极端下载场景有价值 |
| 运维/清理成本 | 10% | 版本淘汰 | 4 / 0.40 | 4 / 0.40 | 均可做生命周期清理 |
| 最终得分（满分5分） | | | **4.00** | 3.30 | 个人工具下载规模极小，静态托管足够 |

**选型决策：**

| 备选方案名称 | 本方案的优点 | 本方案的风险和缺点 | 最终选择 |
| --- | --- | --- | --- |
| 方案1: 后端静态文件托管 | 零服务；同机部署；Range 原生 | 下载带宽受 uvicorn 单进程限制（个人规模足够） | **✓ 采用** |
| 方案2: 对象存储 | 高并发/大文件扩展 | 新增服务与密钥管理，个人工具过重 | — |

#### 1.2.5.5.6. 方案对业务的约束

- **体验约束**：下载失败/校验失败提供重试与"暂仍使用旧版"出口；`force=1` 不可绕过二次弹出但可暂缓使用旧版（不强制卸载视角）。
- **发布约束**：APK 上传后 MD5 由后端自动计算；`enabled=false` 的版本不出现在 `GET /app/version`。
