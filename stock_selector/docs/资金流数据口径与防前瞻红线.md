# 资金流数据口径与防前瞻红线（任务 #171 阶段 1 固化）

> 信息仅供参考，不构成投资建议。

**定位**：这份文档是 `data/fund_flow/daily/` 这套数据的**唯一口径真源**。
代码改动、接口换源、补抓策略调整都不允许改变这里写的语义；
要改口径必须先改这份文档，再改 `stock_selector/fundflow/store.py`。

写它的直接原因：这一条线要攒**至少 12 个月**才允许做第一次实验（见第六节门槛）。
一年之后没有人记得当初为什么这么存，届时唯一能依赖的就是「约定被写下来了」。

## 一、数据源与它的硬约束

| 通道 | 接口 | 能给什么 | 不能给什么 |
|---|---|---|---|
| daily（主通道） | 东财 `push2.eastmoney.com/api/qt/clist/get` | **当天**全市场约 5,9xx 只个股的分档净流入 + 成交额（约 60 页 × 100 行） | 历史。收盘后一过就取不到那一天 |
| 逐只历史（只用于补抓） | 东财 `push2his…/stock/fflow/daykline/get` | 单只票最近约 **124 个交易日**的分档净流入 | 成交额（要从日线/快照 join）；且本机 IP 被严重节流 |
| rank / industry | 同花顺（默认）、东财排行 | 采集时刻的排行快照 | 只落快照，不参与日分区 |

两条必须记住的事实：

1. **主通道不可回溯**。所以「每天准点跑」本身就是数据完整性的一部分，
   一次漏采就是永久缺一天（除非那天还在逐只历史的 124 日窗口内）。
2. **逐只历史被节流到不可用作主通道**：实测跑 3 小时 36 分只写进 134/5,215 只。
   这条线已经退出主采集，只保留「有界补抓」的角色（`--repair-budget`，默认每轮 40 只，轮转游标）。

`rank`/`industry` 只在**交易日**写：快照的日期必须有对应的交易日，
否则会出现「周六的资金流排行」这种没法用的脏文件（旧版本就是这么写的，已修）。

### HTTP 通道：curl_cffi（默认），但它不是免死金牌（2026-10-17 实测）

采集默认走 `curl_cffi`（Chrome 的 TLS/HTTP2 指纹 + 进程内复用连接），`--transport requests` 可退回。
依据是**同一时间窗内两臂交错发同样的请求**（各 8~16 次）：

| 时段形态 | requests | curl_cffi |
|---|---|---|
| 软节流（单发能过） | 0/16 | 7/16，单页中位 115ms（requests 162ms） |
| 硬窗口 | 0/10 | 0/10 |

两条结论要记住，别再重复试：

1. **换域名轮换没用**。`push2`、`1.push2`、`33.push2`、`92.push2`、`push2delay` 六个镜像在
   同一刻一起断连（curl: 56），这道闸按 IP 计，不按域名计。
2. **硬窗口只能等**。所以第 1 页用「分钟级慢梯子 + 整轮重来」（`PAGE1_*` / `ROUND_*`），
   而翻页失败只降速不硬扛——批量接口只给当下，第 1 页取不到就是永久缺一天。

### 浏览器身份：每轮采集开跑前先现种一份落盘（2026-10-27 改口径）

这两个接口（批量 `clist` 与逐只 `push2his`）的匿名身份只能由东财页面自己的 JS 种出来，
直接要 HTTP 响应头是空的，所以种它必须起一次 headless Chrome（`refresh_em_cookie.py`），
落盘到 `data/fund_flow/em_cookie.txt`，会话重建时读进 `Cookie` 头。

改之前的口径是「一天一次」：文件是今天种的就直接用。2026-10-27 按「爬虫跑之前先取 cookie
存文件」改成**每轮采集前都现种**（`_ensure_fresh_identity()`，一个进程只种一次），两个入口
都覆盖：`run_daily`（第 1 页之前）和 `run_repair`（第一个逐只请求之前，没缺口就不开 Chrome）。

- **为什么值得**：节流是按会话累计的。带着一颗当天已经翻过 60 页的身份再跑一轮（补数据、
  当天重跑），第 1 页就可能被掐，而批量接口只给当下——那一天就永久缺，只能靠很慢的逐只补。
- **代价**：每轮多约 25 秒起一次 Chrome；同一轮里批量 + 补抓只种一次，不重复开机。
- **失败不算错误**：起不了浏览器只记 warning、维持原来的节奏，绝不为刷身份把整轮采集拖死。
- 翻页中途连续两页被掐时的「现种换新会话」自救保持不变。

## 二、存储契约

```
data/fund_flow/
    daily/YYYY-MM-DD.parquet     # 一个交易日一个文件
    rank/YYYY-MM-DD.parquet      # 仅交易日
    industry/YYYY-MM-DD.parquet  # 仅交易日
    status.json                  # 最近一次运行读数 + 告警去重日
```

四条不可违反的约定：

1. **分区键是数据自己的交易日，不是采集当天的墙上日期**。
   具体来源：接口 `f124`（这批行的行情时刻，Unix 秒）折算成 Asia/Shanghai 的日期。
   周末或收盘后重跑，只会刷新同一个交易日的分区，不会造出新的日子。
2. **主键 `(trade_date, code)` 唯一**。同一天被采多次时按 `combine_first` 合并：
   **新值非空才覆盖旧值**。这样任何一次成功都不会被另一次失败抹掉，重复写入也不会翻倍。
3. **每行都带两个时间戳**：`data_ts`（这份数据自己的时刻）与 `collected_at`（本次抓取时刻）。
   防前瞻靠这两个字段可审计，不靠口头承诺（见第五节）。
4. **不删旧行**。补抓、重抓都是合并而不是覆盖；停牌/ST 的行只打标记、不物理剔除
   （剔与不剔是读时选择，物理删掉之后截面有多少票就永远说不清了）。

## 三、字段口径

原始量（接口原样，单位：元）：

- `close`、`pct_change`
- `amount` —— 当日成交额。**它是标准化的唯一分母**
- 五档净流入：`main_net_inflow`（主力 = 超大单 + 大单）、`xlarge_net_inflow`（超大单）、
  `large_net_inflow`（大单）、`medium_net_inflow`（中单）、`small_net_inflow`（小单）

派生量（本层自己算，`*_ratio`）：

```
{tier}_ratio = {tier}_net_inflow ÷ amount        （amount ≤ 0 或缺失时留 NaN）
```

- **为什么必须自己算**：接口也发一个占比字段（`f184`），实测与 `f62/f6` 一致但只有两位小数。
  同一个定义留两份不同精度的数，以后一定会让人猜该用哪一份。
- **为什么不填 0**：「净流入恰好为零」与「今天根本没有成交」在因子里是两件事，
  填 0 会把停牌票伪装成「资金平衡」的票。
- `amount` 的来源：主通道直接给；补抓与旧数据迁移从 `data/market_snapshot/<date>.parquet`
  取，取不到再从 `data/stock_kline/<code>.parquet` 的 `amount` 列 join。
  **三个来源必须同单位（元），已用 600000/000001/000002 实测对齐**：分母差 10⁴ 会让
  同一天的 `*_ratio` 差一万倍，而这种错在截面分布上看起来只是「一部分票占比特别大」，
  所以三条来源的单位属于口径，不属于实现细节。

## 四、质量标记

`exclude_reason` 三个取值，`valid = (exclude_reason 为空)`：

| 标记 | 判据 | 含义 |
|---|---|---|
| `zero_amount` | `amount == 0` | 停牌 / 无成交。这是**事实**，所有净流入此时无意义 |
| `no_amount` | `amount` 缺失 | 成交额没并回来（历史迁移会撞上）。这是**缺数**，与上面必须分开记，否则以后没法判断覆盖率 |
| `abnormal_name` | 名称含 `ST` 或「退」 | 异常标的。长期实验的截面口径要剔它，但行留着 |

读侧默认口径：`valid == True`。做稳健性检查时才比较「含 ST」与「不含 ST」两版。

## 五、防前瞻红线（硬性，任何实验不得越过）

> **T 日的资金流只能用于 T+1 日的选股与决策。任何回测都禁止用当日资金信号买入当日个股。**

这条不是保守，而是数据的物理性质：主通道采的是**当天累计到收盘**的分档净额，
16:30 才落盘。也就是说 **T 日这份数据在 T 日盘中根本不存在**——
在回测里用 T 日 ratio 去决定 T 日的开盘/盘中成交，是拿一个当时还没生成的数当依据。

落地要求（写预注册时必须逐条列进验收）：

1. **入场最早时点 = T+1 开盘**。信号日 `trade_date = T`，成交时点只能是 `T+1` 的开盘价
   （或更晚），用当日收盘价买入同样违规——收盘前的资金流累计值不可得。
2. **可审计**：任何一行的 `data_ts` 必须**严格早于**使用它的决策时点。
   审计方法就是把 join 后的表按 `决策时刻 >= data_ts` 断言一遍；
   `collected_at` 用来证明「这份数据确实是在收盘后才抓到的」，两者都要留在表里。
3. **不许用 `collected_at` 代替 `data_ts`**。采集时刻是运行脚本的时间，
   周末补抓出来的 124 天历史 `collected_at` 都一样，只有 `data_ts` 区分得开是哪一天。
4. **迁移/补抓出来的历史同样受这条约束**。`stamp_history()` 把补抓行的 `data_ts` 写成
   它自己的交易日（接口不给逐行时刻，日级能诚实标注的最细粒度就是日期），
   这已经足够支持「T+1 入场」，但**不足以支持任何盘中口径的资金流研究**。

## 六、覆盖度自检与告警

每次运行结束都会做一次自检（不需要单独命令）：

- **应有交易日**：取 `stock_selector/fundflow/store.py` 里 5 只锚票
  （600000/600036/600519/601398/000001）在 `data/stock_kline/` 的日线日期的**交集**最后 N 天。
  用交集不用并集：某只偶然停牌一天时，交集只是少认一天（少查一天，无害），
  并集则会把没开市的日子认成交易日，变成天天假警报。
- `missing` = 应采而根本没有文件的日子。
- `thin`（薄日）= 有文件但行数 < **水位**。水位 = 已存分区行数的中位数 × **0.95**
  （2026-10-27 从 0.8 提上来：那天 16:30 一轮 15 页失败只写 4,500 行、正常 5,925，占中位数 87%，
  0.8 判「已完整」⇒ 当晚不重取，而批量接口只给当下，过午夜这一天永久欠着）；
  分区不足 5 个时不判薄（冷启动会把第一天报成故障）。
  提系数的代价要说清：一个**真的**只有 90% 票的日子（大面积停牌之类）会被判薄 ⇒ 当晚多跑一整轮
  60 页（约 40 秒 + 请求配额），并且自检会推一条钉钉、此后再推 30 天（历史日补不回来，直到滑出检查窗口）。
  实测存量分区里没有一天落在 0.8~0.95 之间（10-14/15/19 那三个半截天 3,689~4,100 行，本来就在水位下），
  所以这次改动不会新增历史假警报。
  这个指标专治「每页都成功、结果只采到一半」——只数文件数是发现不了的。
- 自检结果写 `logs/fund_flow_YYYYMMDD.log` 与 `data/fund_flow/status.json`
  （成功条数、缺失清单、薄日清单、本轮补抓只数与失败个股清单）。
- **断采告警**：`missing` 或 `thin` 非空时推钉钉（复用页面「通知渠道」，同一天只推一条，
  发送失败不记日期、下一轮重试）。
- **当晚重取（2026-10-27 加，`config/inputs.conf` 里同脚本两段）**：16:30 全量采集 +
  **20:30 `--only daily`** 再跑一次。理由是通道性质：批量接口只给「当下」的快照，过午夜这一天就再也取不到，
  所以 16:30 只采到半截（例：10-27 15 页失败只写 4,500 行 / 正常 5,925）时，**只有当晚再跑才抢得回来**。
  幂等由上面的水位保证：分区 ≥ 水位 ⇒ 只花 1 个请求判一下就跳过整轮（好日子约 10~20 秒，含现种一次浏览器身份）；
  分区 < 水位 ⇒ 重取整轮 60 页（约 40~60 秒），按 code 合并，已有值零改写零抹空（10-27 手动那次实测）。
  两点边界要认：① `maybe_alert` 同一天只推一条，所以 16:30 推过「薄日」的晚上，20:30 补成功**不会再推「已修复」**，
  只体现在日志与 `status.json` 的最后一轮；② 20:30 与 20:00/20:10 的 conviction 样本、训练任务同时段（CPU 重叠，
  不抢数据源）。段名不能与 16:30 那段重复——configparser `strict=True` 会抛 `DuplicateSectionError`，
  而 `systems/conf.py` 把异常吞掉 ⇒ **整份 conf 解析成 0 个任务、所有定时任务静默停摆**；
  这条由 `tests/test_scheduler_conf.py` 钉住（顺带钉两段各自的 trigger 与 `--only daily`）。
- **补抓的边界**（`--repair-budget` / `--repair-thin`）：漏采只能走逐只历史接口，
  它既被节流、又只留约 124 个交易日，所以补抓有三条硬约束——
  每轮只补 `--repair-budget` 只（默认 40）、**墙钟上限 180 秒**（`REPAIR_MAX_SECONDS`）、
  游标轮转（每轮从上次停的地方接着走，否则永远只补票池最前面那几只）。
  **薄日默认只报不补**：把一天从几百行补到满票池要几千次逐只请求，
  而逐只请求和主通道抢同一份配额。
  2026-10-17 的事故就是这么来的：旧版逐只作业从 18:00 跑了 4 小时 22 分、1,270 次重试，
  把本机 IP 打进东财黑名单，结果连「一天 60 个请求」的批量通道都取不到数。
  补抓能吃掉全天配额 = 自我 denial-of-service，宁可让告警把人叫起来。

### 首周试运行的降量口径（2026-10-17 拍板）

批量通道**还没有做过一次真实全量验证**（IP 在黑名单里），所以首周按下面的顺序放量：

1. 头三天只翻前 20 页（`--max-pages 20`），连续 3 个交易日全页无 `RemoteDisconnected`
   才升到 40 页，最后回到默认 60 页；
2. 每次跑完先核对三件事：当日分区行数、薄日标记、告警文案是否正常；
3. 连续两页取不到就**自动把页间隔拉长 3 倍**（上限 `PAGE_SLEEP_MAX`），不靠加重试硬扛。

必须记在这里的代价：`--max-pages` 停手等于**故意留一个部分覆盖的交易日**——
批量接口只给「当下」，这一天之后取不回来，只能靠逐只补抓（有界预算 + 180 秒上限，
补满一天要几十轮）。所以**降速（`--page-sleep`）优先于降量（`--max-pages`）**：
前者票池仍然完整、只是慢一点，后者直接欠数据。试运行这几天欠的行数要在台账里认下来。

## 七、实验启动门槛（阶段 3，绝不提前越线）

同时满足两条才允许写第一个资金流预注册、才允许开正式回测：

1. **连续满 12 个月完整交易日**，且期间没有超过 **3 天**的断档；
2. **样本窗 ≥ 250 个交易日**，并预留 **≥ 20% 的留出段**。

在这之前不做的三件事（避免回到历史上反复失效的老路）：

- 不用短期样本先跑出正向结果、再事后补规则；
- 不为资金流新增任何因子、策略逻辑或回测代码改动（阶段 1 只做数据管道）；
- 不花钱买第三方历史数据、不做大规模强回溯——只增量攒。

实验一旦开跑，规格固定：**实验组 + 躺平对照组 + Δ 差值 + 单调性校验**，
并且第五节的防前瞻断言必须出现在验收清单里。

## 八、预注册 FF-1：主力占比有没有前向信息（2026-10-27 定稿，读数出来之前不许改）

### 0. 先认下来：这一节是第七节门槛之外的例外

第七节的两条门槛**没有满足**：资金流目前只有 127 个满票池日（最早 2026-04-14），
够不上「连续 12 个月 / ≥250 交易日」；留出段的 20.7% 是靠切法凑出来的，不是攒出来的。
第七节第二条也明写了「不为资金流新增任何因子或回测代码改动」。
2026-10-27 用户拍板先做一次「到底有没有预测力」的只读预注册，接受的约束是：

- 产物只有这一节 + 一个只读脚本 `scripts/fund_flow_signal_read.py`；
  **不写策略、不出榜、不改打分链、不动 `config/inputs.conf`、不发钉钉、不写生产库**，明细只落 `/tmp`；
- 下面第 5 小节的门槛在**任何读数存在之前**写死，出来后不许回头改口径；判「不够格」就照实报不够格；
- 样本长度是这份读数最大的短板：127 天只有一个半年段，跨市场状态的稳健性它答不了。

### 1. 窗口（按当日分区行数实测划定，不按日历推）

| 段 | 日期 | 交易日 | 用途 |
|---|---|---|---|
| 不可用 | 2026-02-02 ~ 04-13 | — | 逐只补抓的累加过程（1~3,660 行/天），不参与 |
| **主窗** | 2026-04-14 ~ 2026-08-31 | **96** | 判门槛 |
| **留出段** | 2026-09-01 ~ 2026-10-13 | **25（20.7%）** | 不参与任何挑选，最后单独复算一次 |
| 半截天 | 10-14、10-15、10-16、10-19 | 排除 | 试运行降量 + IP 黑名单欠的行（4,059 / 3,689 / 186 / 4,100 行） |
| 满票池对照 | 2026-10-20 ~ 10-27 | 6 | 只报「口径换成今天这套 5,925 只的池子，结论变不变」，不进主表 |

满票池日 = 当日分区行数 ≥5,000（含深市创业板段的采集）。10-14/15/19 那三天行数在 3,689~4,100，
按第六节的水位（**当时**是中位数×0.8）**被判成「已完整」而没重取**——这正是水位那个洞咬人的地方，
所以这几天只能整段排除，不许「勉强用上」。（水位读数后已提到 ×0.95，见 §六；那三天本来就在新水位线下，
重取通道只当晚有效，历史这几天补不回来。）

### 4″. 价格空间（2026-10-27 读数前的更正，不是事后加规则）

原口径第 4 小节写「行情源 = qlib 前复权面板」。核对后这条前提是**错的**，证据三条：

1. 面板 `$factor` 恒为 1.0（实测 2026-04-01→10-27 抽票逐日全 1）；
2. 面板收盘价与 `data/stock_kline` 的**未复权**日线逐日相同（冒烟窗口 8,692 格里，
   裸价涨幅与东财 `pct_change` 差 >0.5 个百分点的只有 5 格，其余完全一致）；
3. 除权日现出原形：**603061 在 2026-04-16 裸价 −26.28%，东财涨幅口径 +7.02%**
   （日线里的 `last_close` 抄的是昨天那个 raw close，不是交易所的除权参考价）。

后果很具体：除权日会被读成「暴跌 26%」，正好落在 `ratio_1d` 最低那几个桶的尾巴上，
足以**凭空造出**「主力流出的票后续还跌」这条假信号——而它是这份读数唯一想回答的问题。
所以本节的价一律按下述两件事分开处理，且都在**任何读数落地之前**定死：

- **合成复权链**：`裸价 × 累积修正系数`。只在「东财涨幅与裸价涨幅差 >0.1pp」的那天乘一次
  `(1+东财涨幅)/(1+裸价涨幅)`，其余天系数为 1。于是**逐日前向收益与东财 `pct_change` 恒等**
  （冒烟实测：修正后与东财差 >0.5pp 的格子 8,692 格里 0 个）。
- **封板判据也走这套价**：交易所的 ±10% 是相对**除权后的参考价**算的，
  用裸价判会把除权日误判成「全天封死跌停」而走顺延那条路（冒烟实测 8,692 格里 2 格分歧；
  改成复权价后分歧 0）。容差 9.8% 这条线不动。
- **停牌冻结行作废**：`data/stock_kline` 在停牌那天补一行 `volume=0`、收盘价照抄前一天
  （实测 2026-05-20 的 000608 / 002047 / 002629）。这种格子不拦就会读成「那天平盘、还能买卖」，
  一律置 NaN ⇒ 走「无行情 → 顺延」那条路。冒烟窗口内 16 格。
- **覆盖面如实报**：修正系数只能来自东财分区，分区没覆盖的日子（存档早期 2026-04-14 之前、
  以及 §1 排除的半截天）修不上；读数日志里报出「东财覆盖不足天数」与「覆盖足但该票无行」的条数。

这条更正**不加任何判据、不改任何门槛**，只是把「价」这件事从错的前提交正过来。

### 4′. 可成交性：涨停买不进、跌停卖不出，而且封板是个过程

用户提的硬约束（2026-10-27 原话要点）：涨停/跌停不是一下出现的，要经过一段时间才封死。
所以不能只看「收盘是不是涨停」，必须区分「开盘就封住」和「开盘没封、后来才封」。

**买入侧（T+1 开盘建仓）**

- 开盘即封 ⇒ 判「买不进」，剔除，并**报出剔了多少条**：`open(T+1) ÷ close(T) − 1 ≥ 9.8%`。
- 开盘没封、当天后来才涨停 ⇒ **不剔**（开盘价是真实能成交的价，正是「涨停要经过一段时间」那一面）。
  这类样本单独成组报读数（看「开盘后封板」的票后续走势是否更好），属描述性分组，**不进主判据、不改门槛**。
- T+1 停牌没有 bar ⇒ 判「无法建仓」，剔除并计数。

**卖出侧（T+1+h 收盘出场）**

- 出场日**全天封死跌停**（`high ÷ 前收 − 1 ≤ −9.8%`，盘中最高价都没脱离跌停）⇒ 卖不出，
  **顺延到下一个可成交交易日的开盘价**，并把**顺延天数**与**顺延期间多吃的跌幅**记进账单独报出——
  这才是「跌停卖不出」的真代价，不能把出场价当作能成交。
- 出场日收盘跌停但盘中打开过 ⇒ 仍按收盘价出场（把最坏那天整个吃下，偏保守），单独计数。
- 顺延超过 10 个交易日仍卖不出 ⇒ 截断，并明写条数与票名。

**两处核对**

- 判封板用的价与东财自带的 `pct_change`（独立第二来源）交叉核对，差异 >0.5 个百分点的样本数报出来；
  同一张表上再报「裸价判涨停/跌停」与「复权价判」各自和东财口径的分歧条数
  （原文第二条「抽 10 个 `factor` 变动的除权日核对」**作废**：本机面板 `$factor` 恒为 1.0，
  没有可抽的除权格，见 §4″。改为直接抽 10 条「裸价与东财差 >0.5pp」的格子人工看是不是除权日）。
- 主板容差 9.8%（留 0.2 个百分点给最小变动价位的取整误差）写死，不许事后调节。

**要认的边界**：日线判不了「几点封板、封单多大、打开几次」。那一层只能用 5m 分时，
而本机分时只覆盖约 3,774 只/日、61 个交易日（§29 实测）⇒ 按第 6 小节做成副臂。

  （占 35 万格的 0.003%）。抽样 10 条除权里最典型的是 603061 @ 2026-04-16：裸价算出来 −26.28%，
  复权后与东财一致 +7.02%。不修这一步，面板会把「跌停」当成「涨停」判、并凭空造出 20 多个百分点的收益。

## 九、App 资金榜：三档窗口的口径与薄日缺口（2026-10-30 10:04 CST 落档）

需求原话：**「资金可以查看最近 3 天、7 天、30 天流入和流出的股票」**，口径他已拍板：
**主力净额 = 超大单 + 大单**（即第三小节的 `main_net_inflow`，不是五档加总）。

这一节只定义「榜」怎么算。**它是展示层，不是信号层**：第八小节 FF-1 已经判过
`ratio_1d/ratio_3d` 没有前向信号（t 0.21~0.47、留出段反号、④样本外≈0），
所以页面上必须写着「不构成买卖依据」，榜本身不给任何买卖价、不接任何下单链路。

### 1. 窗口按交易日，不按日历日

「最近 3 天」= 最近 3 个**有分区的交易日**（跳过周末与长假）。按日历日切的话，
国庆后第一天点 7 日档会只覆盖 3 个交易日，同一句「7 天」在不同日期意味着不同的事。

**交易日日历取自分区文件名**（`data/fund_flow/daily/*.parquet` 的 stem），不是从数据行里数。
这条是被测试逼出来的：如果从行里数，某只票缺一天只会让日历跟着缩短一天，
它会「假装完整」地进榜——于是**「那天没采到」在页面上显示成「这只票那天没有资金动向」**，
这正是第一~六小节反复在防的静默缺数。测试 `test_fund_rank.py::test_calendar_shorter_than_window_yields_no_rows`
和 `test_build_uses_partition_file_names_as_the_calendar` 钉住这一点。

### 2. 一行榜单的字段口径

| 字段 | 算法 | 为什么这么定 |
| --- | --- | --- |
| `net_inflow` | 窗口内 `main_net_inflow` 求和（元） | 他点名的口径；前端换成「亿」只是量纲换词 |
| `turnover` | 窗口内 `amount` 求和（元） | 占比的分母必须与分子同窗口，否则单日的钱除以多日的量 |
| `ratio` | `net_inflow ÷ turnover` | 与第三小节 `main_ratio` 同一定义，只是分母换成窗口合计 |
| `ret_pct` | 窗口内日 `pct_change` **复利累乘** | §49 之后日线存裸价，直接首尾相除会在除权日打出一根假柱 |
| `days` | 该票在窗口内实际命中的天数 | 让页面能显示「凑满 3/3」还是缺数 |
| 进榜资格 | 窗口内**每一天都要有且 `valid=True`** | 缺一天不进榜。宁可榜单短，也不给半窗口的净额贴上「3 日」的标签 |

`valid=False` 的行（第三/四小节的质量标记）同样剔掉，不参与求和也不占天数。

### 3. 实测读数（as_of 2026-10-29，10,546 只票入表）

```
3 日档：5,373 只进榜      7 日档：5,173 只进榜      30 日档：0 只进榜
```

**30 日档为空不是 bug，是采集缺口。** 最近 30 个交易日里有四天采薄了：

| 日期 | 分区行数 | 正常水位 |
| --- | --- | --- |
| 2026-10-14 | 4,059 | ≈5,210 |
| 2026-10-15 | 3,689 | ≈5,210 |
| 2026-10-16 | **186** | ≈5,210 |
| 2026-10-19 | 4,100 | ≈5,210 |

按第 2 条的资格规则，这四天落在 30 日窗口内 ⇒ 没有任何票能凑满 30 天 ⇒ 这一档 0 只。
薄日由 `fetch_fund_flow.py` 的自检写在 `data/fund_flow/status.json`（第六小节「薄日只报不补」），
构建脚本把它带进 `meta.thin_days`，读取层拼成一句 `notice`，页面抬头原样念出来。
**没采到不能显示成「没有资金动向」**——所以点 30 日档时看到的原因是「10-16 只采到 186 行」，
而不是一个空榜或消失的档位。
