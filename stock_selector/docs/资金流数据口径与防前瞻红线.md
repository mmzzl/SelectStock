# 资金流数据口径与防前瞻红线（任务 #171 阶段 1 固化）

> 信息仅供参考，不构成投资建议。

**定位**：这份文档是 `data/fund_flow/daily/` 这套数据的**唯一口径真源**。
代码改动、接口换源、补抓策略调整都不允许改变这里写的语义；
要改口径必须先改这份文档，再改 `stock_selector/fundflow/store.py`。

写它的直接原因：这一条线要攒**至少 12 个月**才允许做第一次实验（见第六节门槛）。
一年之后没有人记得当初为什么这么存，届时唯一能依赖的就是「约定被写下来了」。

## 一、数据源与它的硬约束

| 通道 | 接口 | 能给什么 | 不能给什么 |
|---|---|---|---|
| daily（主通道） | 东财 `push2.eastmoney.com/api/qt/clist/get` | **当天**全市场约 5,9xx 只个股的分档净流入 + 成交额（约 60 页 × 100 行） | 历史。收盘后一过就取不到那一天 |
| 逐只历史（只用于补抓） | 东财 `push2his…/stock/fflow/daykline/get` | 单只票最近约 **124 个交易日**的分档净流入 | 成交额（要从日线/快照 join）；且本机 IP 被严重节流 |
| rank / industry | 同花顺（默认）、东财排行 | 采集时刻的排行快照 | 只落快照，不参与日分区 |

两条必须记住的事实：

1. **主通道不可回溯**。所以「每天准点跑」本身就是数据完整性的一部分，
   一次漏采就是永久缺一天（除非那天还在逐只历史的 124 日窗口内）。
2. **逐只历史被节流到不可用作主通道**：实测跑 3 小时 36 分只写进 134/5,215 只。
   这条线已经退出主采集，只保留「有界补抓」的角色（`--repair-budget`，默认每轮 40 只，轮转游标）。

`rank`/`industry` 只在**交易日**写：快照的日期必须有对应的交易日，
否则会出现「周六的资金流排行」这种没法用的脏文件（旧版本就是这么写的，已修）。

### HTTP 通道：curl_cffi（默认），但它不是免死金牌（2026-10-17 实测）

采集默认走 `curl_cffi`（Chrome 的 TLS/HTTP2 指纹 + 进程内复用连接），`--transport requests` 可退回。
依据是**同一时间窗内两臂交错发同样的请求**（各 8~16 次）：

| 时段形态 | requests | curl_cffi |
|---|---|---|
| 软节流（单发能过） | 0/16 | 7/16，单页中位 115ms（requests 162ms） |
| 硬窗口 | 0/10 | 0/10 |

两条结论要记住，别再重复试：

1. **换域名轮换没用**。`push2`、`1.push2`、`33.push2`、`92.push2`、`push2delay` 六个镜像在
   同一刻一起断连（curl: 56），这道闸按 IP 计，不按域名计。
2. **硬窗口只能等**。所以第 1 页用「分钟级慢梯子 + 整轮重来」（`PAGE1_*` / `ROUND_*`），
   而翻页失败只降速不硬扛——批量接口只给当下，第 1 页取不到就是永久缺一天。

## 二、存储契约

```
data/fund_flow/
    daily/YYYY-MM-DD.parquet     # 一个交易日一个文件
    rank/YYYY-MM-DD.parquet      # 仅交易日
    industry/YYYY-MM-DD.parquet  # 仅交易日
    status.json                  # 最近一次运行读数 + 告警去重日
```

四条不可违反的约定：

1. **分区键是数据自己的交易日，不是采集当天的墙上日期**。
   具体来源：接口 `f124`（这批行的行情时刻，Unix 秒）折算成 Asia/Shanghai 的日期。
   周末或收盘后重跑，只会刷新同一个交易日的分区，不会造出新的日子。
2. **主键 `(trade_date, code)` 唯一**。同一天被采多次时按 `combine_first` 合并：
   **新值非空才覆盖旧值**。这样任何一次成功都不会被另一次失败抹掉，重复写入也不会翻倍。
3. **每行都带两个时间戳**：`data_ts`（这份数据自己的时刻）与 `collected_at`（本次抓取时刻）。
   防前瞻靠这两个字段可审计，不靠口头承诺（见第五节）。
4. **不删旧行**。补抓、重抓都是合并而不是覆盖；停牌/ST 的行只打标记、不物理剔除
   （剔与不剔是读时选择，物理删掉之后截面有多少票就永远说不清了）。

## 三、字段口径

原始量（接口原样，单位：元）：

- `close`、`pct_change`
- `amount` —— 当日成交额。**它是标准化的唯一分母**
- 五档净流入：`main_net_inflow`（主力 = 超大单 + 大单）、`xlarge_net_inflow`（超大单）、
  `large_net_inflow`（大单）、`medium_net_inflow`（中单）、`small_net_inflow`（小单）

派生量（本层自己算，`*_ratio`）：

```
{tier}_ratio = {tier}_net_inflow ÷ amount        （amount ≤ 0 或缺失时留 NaN）
```

- **为什么必须自己算**：接口也发一个占比字段（`f184`），实测与 `f62/f6` 一致但只有两位小数。
  同一个定义留两份不同精度的数，以后一定会让人猜该用哪一份。
- **为什么不填 0**：「净流入恰好为零」与「今天根本没有成交」在因子里是两件事，
  填 0 会把停牌票伪装成「资金平衡」的票。
- `amount` 的来源：主通道直接给；补抓与旧数据迁移从 `data/market_snapshot/<date>.parquet`
  取，取不到再从 `data/stock_kline/<code>.parquet` 的 `amount` 列 join。
  **三个来源必须同单位（元），已用 600000/000001/000002 实测对齐**：分母差 10⁴ 会让
  同一天的 `*_ratio` 差一万倍，而这种错在截面分布上看起来只是「一部分票占比特别大」，
  所以三条来源的单位属于口径，不属于实现细节。

## 四、质量标记

`exclude_reason` 三个取值，`valid = (exclude_reason 为空)`：

| 标记 | 判据 | 含义 |
|---|---|---|
| `zero_amount` | `amount == 0` | 停牌 / 无成交。这是**事实**，所有净流入此时无意义 |
| `no_amount` | `amount` 缺失 | 成交额没并回来（历史迁移会撞上）。这是**缺数**，与上面必须分开记，否则以后没法判断覆盖率 |
| `abnormal_name` | 名称含 `ST` 或「退」 | 异常标的。长期实验的截面口径要剔它，但行留着 |

读侧默认口径：`valid == True`。做稳健性检查时才比较「含 ST」与「不含 ST」两版。

## 五、防前瞻红线（硬性，任何实验不得越过）

> **T 日的资金流只能用于 T+1 日的选股与决策。任何回测都禁止用当日资金信号买入当日个股。**

这条不是保守，而是数据的物理性质：主通道采的是**当天累计到收盘**的分档净额，
16:30 才落盘。也就是说 **T 日这份数据在 T 日盘中根本不存在**——
在回测里用 T 日 ratio 去决定 T 日的开盘/盘中成交，是拿一个当时还没生成的数当依据。

落地要求（写预注册时必须逐条列进验收）：

1. **入场最早时点 = T+1 开盘**。信号日 `trade_date = T`，成交时点只能是 `T+1` 的开盘价
   （或更晚），用当日收盘价买入同样违规——收盘前的资金流累计值不可得。
2. **可审计**：任何一行的 `data_ts` 必须**严格早于**使用它的决策时点。
   审计方法就是把 join 后的表按 `决策时刻 >= data_ts` 断言一遍；
   `collected_at` 用来证明「这份数据确实是在收盘后才抓到的」，两者都要留在表里。
3. **不许用 `collected_at` 代替 `data_ts`**。采集时刻是运行脚本的时间，
   周末补抓出来的 124 天历史 `collected_at` 都一样，只有 `data_ts` 区分得开是哪一天。
4. **迁移/补抓出来的历史同样受这条约束**。`stamp_history()` 把补抓行的 `data_ts` 写成
   它自己的交易日（接口不给逐行时刻，日级能诚实标注的最细粒度就是日期），
   这已经足够支持「T+1 入场」，但**不足以支持任何盘中口径的资金流研究**。

## 六、覆盖度自检与告警

每次运行结束都会做一次自检（不需要单独命令）：

- **应有交易日**：取 `stock_selector/fundflow/store.py` 里 5 只锚票
  （600000/600036/600519/601398/000001）在 `data/stock_kline/` 的日线日期的**交集**最后 N 天。
  用交集不用并集：某只偶然停牌一天时，交集只是少认一天（少查一天，无害），
  并集则会把没开市的日子认成交易日，变成天天假警报。
- `missing` = 应采而根本没有文件的日子。
- `thin`（薄日）= 有文件但行数 < **水位**。水位 = 已存分区行数的中位数 × 0.8；
  分区不足 5 个时不判薄（冷启动会把第一天报成故障）。
  这个指标专治「每页都成功、结果只采到一半」——只数文件数是发现不了的。
- 自检结果写 `logs/fund_flow_YYYYMMDD.log` 与 `data/fund_flow/status.json`
  （成功条数、缺失清单、薄日清单、本轮补抓只数与失败个股清单）。
- **断采告警**：`missing` 或 `thin` 非空时推钉钉（复用页面「通知渠道」，同一天只推一条，
  发送失败不记日期、下一轮重试）。
- **补抓的边界**（`--repair-budget` / `--repair-thin`）：漏采只能走逐只历史接口，
  它既被节流、又只留约 124 个交易日，所以补抓有三条硬约束——
  每轮只补 `--repair-budget` 只（默认 40）、**墙钟上限 180 秒**（`REPAIR_MAX_SECONDS`）、
  游标轮转（每轮从上次停的地方接着走，否则永远只补票池最前面那几只）。
  **薄日默认只报不补**：把一天从几百行补到满票池要几千次逐只请求，
  而逐只请求和主通道抢同一份配额。
  2026-10-17 的事故就是这么来的：旧版逐只作业从 18:00 跑了 4 小时 22 分、1,270 次重试，
  把本机 IP 打进东财黑名单，结果连「一天 60 个请求」的批量通道都取不到数。
  补抓能吃掉全天配额 = 自我 denial-of-service，宁可让告警把人叫起来。

### 首周试运行的降量口径（2026-10-17 拍板）

批量通道**还没有做过一次真实全量验证**（IP 在黑名单里），所以首周按下面的顺序放量：

1. 头三天只翻前 20 页（`--max-pages 20`），连续 3 个交易日全页无 `RemoteDisconnected`
   才升到 40 页，最后回到默认 60 页；
2. 每次跑完先核对三件事：当日分区行数、薄日标记、告警文案是否正常；
3. 连续两页取不到就**自动把页间隔拉长 3 倍**（上限 `PAGE_SLEEP_MAX`），不靠加重试硬扛。

必须记在这里的代价：`--max-pages` 停手等于**故意留一个部分覆盖的交易日**——
批量接口只给「当下」，这一天之后取不回来，只能靠逐只补抓（有界预算 + 180 秒上限，
补满一天要几十轮）。所以**降速（`--page-sleep`）优先于降量（`--max-pages`）**：
前者票池仍然完整、只是慢一点，后者直接欠数据。试运行这几天欠的行数要在台账里认下来。

## 七、实验启动门槛（阶段 3，绝不提前越线）

同时满足两条才允许写第一个资金流预注册、才允许开正式回测：

1. **连续满 12 个月完整交易日**，且期间没有超过 **3 天**的断档；
2. **样本窗 ≥ 250 个交易日**，并预留 **≥ 20% 的留出段**。

在这之前不做的三件事（避免回到历史上反复失效的老路）：

- 不用短期样本先跑出正向结果、再事后补规则；
- 不为资金流新增任何因子、策略逻辑或回测代码改动（阶段 1 只做数据管道）；
- 不花钱买第三方历史数据、不做大规模强回溯——只增量攒。

实验一旦开跑，规格固定：**实验组 + 躺平对照组 + Δ 差值 + 单调性校验**，
并且第五节的防前瞻断言必须出现在验收清单里。
